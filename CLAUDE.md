# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Descripción del proyecto

**SGO Tublood** — Sistema de Gestión de Observaciones para Tublood SA (empresa argentina de dispositivos médicos). Monolito Laravel 13 + Vue 3 + Inertia.js. Sin API REST separada; Inertia maneja toda la comunicación cliente-servidor mediante formularios y redirects estándar.

**Estado**: en desarrollo activo. Terminados: autenticación, CRUD de usuarios/roles (con sector, supervisor y gerente), carga masiva de usuarios por Excel, motor de alertas por vencimiento del plazo de gestión, portal público de carga de observaciones (sin login, con múltiples productos por observación en "Falla de Producto"), listado/edición admin de observaciones (modal que asigna responsable/sector, clasifica con prioridad/tipo de caso — al completar ambos una observación `pendiente_clasificacion` pasa a `clasificada` — y cambia el estado, con autorización por objeto), CRUD de clientes con clasificación documental (tipo de cliente, checklist de documentos requeridos con Sí/No y vencimiento, estado calculado) y archivos adjuntos, campana de notificaciones de clientes por vencer, dashboard con estadísticas reales, integración de sincronización de clientes con RP Sistemas (ERP), tabla de sectores sembrada, el módulo de No Conformidades entero (circuito propio, vínculo con observaciones en las dos direcciones y recordatorios de plazos) y una librería de componentes Vue compartidos. Pendiente: clasificación (Garantía de Calidad), derivación entre sectores, SLA configurable por prioridad (hoy el plazo es fijo por sector), envío real de emails (el driver sigue en `log`), modo oscuro para el portal público. Ver [docs/ARQUITECTURA-SGO.md](docs/ARQUITECTURA-SGO.md) para reglas de negocio, modelo de datos completo y hoja de ruta por fases — es la fuente de verdad para partes del dominio aún no implementadas (p. ej. campos de "Disconformidad de Servicio", que dependen del `Especificacion-Tecnica-SGO-v3.docx`). `docs/Notas-Finales-Prototipo.md` es un addendum posterior con ajustes de reglas de negocio (p. ej. flujo de clasificación y de derivación entre sectores) que **prevalece sobre `ARQUITECTURA-SGO.md`** en caso de discrepancia.

```bash

# Alertas

# Base de datos
php artisan migrate         # ejecutar migraciones pendientes
php artisan db:seed         # re-seedear roles/permisos/usuario admin (RolesAndPermissionsSeeder)
php artisan tinker          # REPL

# Caché
php artisan cache:clear     # también limpia la caché de permisos de Spatie
php artisan config:clear
```

Usuario semilla por defecto: `admin@admin.com` / `password` (rol: `super-admin`).

## Arquitectura

### Flujo de una request (área admin, autenticada)
```
HTTP → Route (middleware: auth, can:permiso) → Controller (authorize) → Eloquent → DB
                                                        ↓
                                        inertia('NombrePagina', $props)
                                                        ↓
                                   Componente Vue 3 (resources/js/Pages/)
```

### Namespacing de controllers
- `app/Http/Controllers/Admin/` — CRUD administrativo autenticado (Users, Roles, Clientes, Observaciones).
- `app/Http/Controllers/Auth/` — login/logout.
- `app/Http/Controllers/Portal/` — rutas **públicas sin autenticación** (portal externo de carga de observaciones). No llevan `$this->authorize()`.
- `app/Http/Controllers/DashboardController.php` — vive suelto en `Controllers/` (no encaja en Admin ni Auth), calcula estadísticas para el panel principal.
- Cuando dos controllers en distinto namespace comparten nombre de clase (p. ej. `Portal\ObservacionController` y `Admin\ObservacionController`), en `routes/web.php` se importa uno con alias (`as AdminObservacionController`).

### Convenciones clave

**Backend**
- La autorización tiene **dos mecanismos** según el caso:
  - **Por permiso** (global): middleware `can:permiso` en la ruta + `$this->authorize('permiso')` en el controller. Es el default para casi todo (`users.*`, `roles.*`, `clientes.*`, `observaciones.view`).
  - **Por objeto** (Policy): cuando la autorización depende del registro puntual, no solo del rol — ver [app/Policies/ObservacionPolicy.php](app/Policies/ObservacionPolicy.php), con **una sola habilidad**:
    - `update` — gestionar el caso (reasignar, reclasificar, cambiar estado, subir/borrar archivos sueltos, comentar en la bitácora): **solo** el `responsable` asignado (o super-admin, vía `Gate::before`). Enganchada en la ruta con `->middleware('can:update,observacion')` y en el controller con `$this->authorize('update', $observacion)` — también gatea `observaciones.bitacora.store`, que hasta el 14/9/2026 usaba una habilidad `comentar` propia y más amplia (sumaba a cualquiera del sector y a los usuarios "a notificar"); se unificó porque se decidió que gestionar un caso, comentar incluido, quede exclusivamente en manos de quien lo tiene asignado. Notificados y gente del sector quedan en solo lectura. ⚠️ Consecuencia: una observación **sin responsable** (recién entrada por el portal, o a la que se le quitó el responsable) solo la toca un super-admin — antes la regla del sector destrababa ese caso al derivar.

    El permiso `observaciones.edit` sigue existiendo en el seeder pero **ya no gatea nada** de esto — quedó de la época en que cualquiera con ese permiso podía editar cualquier observación; hoy solo habilita la carga manual.
  - Rutas de `Portal/` son públicas por diseño, sin `$this->authorize()`.
- `super-admin` saltea **todos** los checks de Gate (tanto permisos como Policies) vía `Gate::before()` en [AppServiceProvider.php](app/Providers/AppServiceProvider.php) — por eso `ObservacionPolicy` no necesita chequear el rol explícitamente, alcanza con comparar `responsable_id`.
- Siempre eager-load relaciones en los controllers (`->with('roles')`, `->with(['responsable:id,name', 'cliente:id,numero,razon_social,mail,telefono', 'productos'])`) para evitar N+1 — y **restringir columnas** en el eager-load cuando el modelo relacionado tiene campos sensibles (p. ej. `User` tiene `password`): usar `'responsable:id,name'`, nunca `'responsable'` a secas si el resultado va a props de Inertia.
- La caché de Spatie dura 24 h — llamar `app(\Spatie\Permission\PermissionRegistrar::class)->forgetCachedPermissions()` cada vez que se muten roles o permisos (ya está en el seeder).
- Modelos con catálogos de valores (estados, orígenes) los declaran como `public const` en el propio modelo — ver `Observacion::ESTADOS` y `Observacion::ORIGENES` en [app/Models/Observacion.php](app/Models/Observacion.php). Reusar esas constantes en las reglas de validación (`'in:' . implode(',', array_keys(Observacion::ESTADOS))`) en vez de hardcodear la lista.
- **Patrón de tabla hija con archivos/ítems repetibles**: `ObservationAttachment`, `ObservationProduct` y `ClienteAttachment` siguen el mismo molde — `foreignId('...')->constrained(...)->cascadeOnDelete()`, `$fillable` plano, relación `belongsTo` de vuelta al padre y `hasMany` en el padre. Los adjuntos (`store('observaciones', 'local')` / `store('clientes', 'local')`) van al disco `local` (privado, `storage/app/private`). **Los adjuntos de observaciones son solo de escritura** (no hay ruta que los sirva); los de clientes sí tienen descarga (`ClienteController::downloadArchivo`, único download real del código — usa `Storage::disk('local')->download(...)`). Ojo con `scopeBindings()` en rutas anidadas: Laravel busca el método de relación por el **plural del nombre del parámetro de ruta** (por eso el parámetro se llama `{attachment}`, no `{archivo}`, para matchear `Cliente::attachments()`).
- **Usuarios a notificar de una observación** (`Observacion::notificados()`, tabla `observation_watchers`) — la **única relación muchos-a-muchos del dominio**. Reciben `ObservacionSeguimientoNotification` **solo al ser sumados** (se compara contra los que ya estaban antes del `sync()`) y pueden ver el caso, pero no gestionarlo ni comentar en su bitácora (ver la habilidad `update` de la Policy más arriba). El cambio queda registrado en la bitácora con acción `notificados`, escrito **desde el controller** (`ObservacionController::sincronizarNotificados()`) y no desde el observer: `sync()` sobre una relación no dispara el evento `updated` del modelo, así que `ObservacionObserver` no se entera solo.
- **Sincronización de clientes** (`ClienteSyncService::sync()`) hace `upsert()` con `numero` como clave. Cualquier columna que se agregue a `clientes` para ser **editable a mano en el panel** (`tipo_cliente`, `tiene_legajo`, `habilitado`, `notas`, `mail_nuevo`) o **derivada** de ellas (`fecha_vencimiento`, `documentacion_completa`) **no debe** agregarse a la lista de columnas del `upsert()`, o la próxima sync (corre cada 5 min) la pisa con lo que traiga el ERP.
- `HandleInertiaRequests` comparte en cada request `notificaciones.vencimientos` (clientes vencidos o por vencer en ≤30 días, gateado por `can('clientes.vencimientos')` — **permiso propio, no `clientes.view`**: seguir los vencimientos es tarea de una persona puntual, hoy solo el rol `calidad_servicio`. La query solo corre si el usuario tiene el permiso, por cortocircuito del ternario) y `notificaciones.alertas` (`unreadNotifications` del usuario). Ambos alimentan la campana en `AppLayout.vue`.

**Frontend**
- Todos los componentes de página van en `resources/js/Pages/`, con el mismo nombre que se pasa a `inertia()` (incluye el subpath: `inertia('Admin/Observaciones/Index')` → `resources/js/Pages/Admin/Observaciones/Index.vue`).
- Componentes reutilizables (no-página) van en `resources/js/Components/`: `Badge`, `Button`, `Modal`, `Pagination`, los de formulario (`Input`, `Select`, `Textarea`, `RadioGroup`, `FormSection`) y dos de dominio (`CampoDinamico`, `CamposUsuario`). **Nunca reimplementar un input inline**: además de duplicar estilo, es así como `CrearInterna.vue` quedó sin modo oscuro cuando se agregó el resto. `Modal` acepta `size="sm"|"lg"|"xl"` y se cierra con click en el backdrop o evento `@close`.
- Los componentes de formulario comparten props: `label`, `error`, `hint` (ayuda debajo, la tapa el error), `required` (dibuja el `*`) y `full` (ocupa las dos columnas de un `FormSection`). `FormSection` da título + separador y acomoda los campos en 2 columnas por defecto (`:columns="1"` para una sola).
- `CampoDinamico` **no tiene estilo propio**: despacha a `Input`/`Select`/`Textarea`/`RadioGroup` según `campo.tipo`. `CamposUsuario` agrupa los campos que comparten el alta y la edición de usuarios (recibe el objeto de `useForm` tipado como `InertiaForm<UserFormData>` y lo muta directo) y solo se parametriza con `modo="crear"|"editar"`.
- Patrón habitual para editar una fila de una tabla sin navegar: un `Modal` controlado por un `ref` en la página `Index.vue` (ver `Admin/Observaciones/Index.vue`) en vez de una página `Edit.vue` separada — usar este patrón para ediciones simples (pocos campos) antes de crear una página dedicada. Cuando el formulario tiene muchos campos y/o subida de archivos (ver `Admin/Clientes/Edit.vue`, `Admin/Users/Edit.vue`), sí se justifica una página `Edit.vue` propia.
- En `Admin/Observaciones/Index.vue`, el botón "Editar" por fila se muestra según `puedeEditar(o)` (`isSuperAdmin || o.responsable_id === user.id`), **no** según un permiso global — refleja la autorización por objeto del backend (`ObservacionPolicy`).
- Alias de import `@/` apunta a `resources/js/`.
- TypeScript en modo strict. Los tipos compartidos están en [resources/js/types/index.d.ts](resources/js/types/index.d.ts) (`User`, `Role`, `Permission`, `PageProps`, `PaginatedData`, `Cliente`, `ClienteAttachment`, `Observacion`, `ObservationProduct`, `Sector`, `AlertaNotificacion`).
- Usar el composable `usePermissions()` ([resources/js/composables/usePermissions.ts](resources/js/composables/usePermissions.ts)) para checks de permisos en el cliente — expone `hasPermission`, `hasRole`, `isSuperAdmin` y `user` (con `id`, útil para comparar contra `responsable_id` en autorización por objeto). Nunca hardcodear nombres de roles en los componentes.
- Campana de notificaciones en [AppLayout.vue](resources/js/Layouts/AppLayout.vue): lee `page.props.notificaciones` (compartido por `HandleInertiaRequests`, no por un fetch aparte) y muestra un badge con la suma de dos grupos — `vencimientos` (clientes por vencer, calculado en vivo) y `alertas` (notificaciones no leídas de observaciones, del canal `database`). Solo las `alertas` se pueden marcar leídas (`notificaciones.leidas`).
- Modo oscuro: composable `useDarkMode()` ([resources/js/composables/useDarkMode.ts](resources/js/composables/useDarkMode.ts)), estado global vía `ref` a nivel de módulo + `localStorage['theme']`, clase `.dark` en `<html>` (Tailwind v4 configurado con `@custom-variant dark` en [resources/css/app.css](resources/css/app.css), no la variante por media-query por defecto). **Solo cubre el panel interno** (`AppLayout` + páginas `Admin/*` + `Dashboard`) — el login y el portal público (`Pages/Auth/Login.vue`, `Pages/Portal/*`) mantienen su diseño de marca fijo a propósito y no tienen clases `dark:`.
- El middleware `HandleInertiaRequests.php` comparte `auth.user` (con roles y permisos) y mensajes flash a todas las páginas vía datos compartidos de Inertia.
- Los íconos son paths SVG de Heroicons embebidos directamente en [AppLayout.vue](resources/js/Layouts/AppLayout.vue) (objeto `icons`).

### Integración RP Sistemas (ERP externo)
- `app/Services/RpSistemas/RpSistemasClient.php` — cliente HTTP de bajo nivel (`Http::baseUrl(...)->withToken(...)`), solo expone `getClientes()` paginado con filtros; **no** tiene lookup por un único cliente.
- `app/Services/RpSistemas/ClienteSyncService.php` — pagina todos los clientes del ERP y hace `upsert` en la tabla local `clientes` (clave `numero`), idempotente.
- Se dispara vía `SyncClientesJob` (cola), comando `php artisan clientes:sync` (con `--sync` para modo síncrono), o el botón "Sincronizar" en `Admin/Clientes/Index.vue`. Programado cada 5 minutos (`everyFiveMinutes()`) en `routes/console.php`.
- ⚠️ **`clientes.php` devuelve el texto doble-codificado** ("AsociaciÃ³n" en vez de "Asociación"): UTF-8 leído como Latin-1 y vuelto a codificar. Medido el 21/9/2026: 503 valores de 3.729 clientes, en `razon_social`, `domicilio`, `localidad`, `contacto` y `nombre_fantasia`. **No es un problema de nuestra base ni del cliente HTTP** — `articulos.php` sale por el mismo `RpSistemasClient` y devuelve bien sus 44 descripciones con acentos ("BAÑO", "DÍAS", "PUÑO"), y `proveedores`/`ventas`/`partidas`/`compras_articulos` están limpias. Lo correcto es que **RP lo arregle de su lado**; mientras tanto se repara al entrar con [Mojibake](app/Support/Mojibake.php), llamado desde `ClienteSyncService::mapear()`.
  - ⚠️ **La conversión es condicional, nunca a ciegas**: un `mb_convert_encoding()` suelto destruiría "BAÑO" y lo haría **cada cinco minutos, en silencio**. Solo se convierte cuando los bytes releídos como Latin-1 forman UTF-8 válido *y* caen en Latin-1 imprimible — eso es lo que distingue lo roto de lo sano. Verificado contra las 212.000 cadenas de texto de la base: cambia 503 y no toca ninguna otra.
  - Es **idempotente**, así que el día que RP corrija el endpoint pasa a ser un no-op y no hay que sacarlo apurado.
  - **No hizo falta migración para reparar lo ya guardado**: las cinco columnas afectadas están en la lista del `upsert()`, así que la primera sync posterior al arreglo las corrige sola.
- Cuando un `Observacion` se crea desde el portal público con un `contacto_numero_cliente`, `Portal\ObservacionController` busca ese número en la tabla local `clientes` (**no** llama al ERP en vivo) y setea `cliente_id` si hay match — ver flujo completo en [app/Http/Controllers/Portal/ObservacionController.php](app/Http/Controllers/Portal/ObservacionController.php).

### Clasificación documental (clientes y proveedores)
- **El catálogo vive en [config/documentacion.php](config/documentacion.php)**, leído por [app/Support/Documentacion.php](app/Support/Documentacion.php) — mismo patrón que `config/incidencias.php` + `TaxonomiaIncidencias`. Define los 10 tipos y, por tipo, qué documentos se exigen: `obligatorio`, `vence` y `determina_vencimiento`. Agregar un tipo o un documento es solo config. De ahí salen el select del panel, el checklist de la ficha, las reglas de validación y las columnas del Excel — ninguno duplica la lista.
- ⚠️ **Un solo catálogo para las dos entidades.** Son las mismas figuras reguladas (un importador es un importador esté de un lado o del otro del mostrador) y los mismos papeles de ANMAT; duplicarlo garantizaba que las dos copias se desincronizaran. Lo único propio de cada una es **qué tipos se ofrecen**, en `config('documentacion.entidades')`: un cliente puede ser cualquiera de los diez, un **proveedor solo seis** (las otras cuatro —profesional independiente, centro médico, veterinaria e institución— le compran a Tublood, no le venden). Sacar un tipo de una lista no rompe lo ya cargado: `Documentacion::etiqueta()` y `::documentos()` buscan en el catálogo **completo** a propósito, así que un registro ya clasificado sigue mostrando su nombre y su checklist aunque su tipo ya no se pueda volver a elegir.
- **La lógica compartida vive en el trait [ClasificacionDocumental](app/Models/Concerns/ClasificacionDocumental.php)** (`documentos()`, `estadoDocumentacion()`, `recalcularEstadoDocumental()`), que usan `Cliente` y `Proveedor`. Cada modelo solo declara de qué columna sale su tipo (`tipo_cliente` / `tipo_proveedor`), qué modelo guarda su checklist (`ClienteDocumento` / `ProveedorDocumento`) y su clave de entidad.
- En el front pasa lo mismo: `Components/ControlDocumental.vue` y `Components/ChecklistDocumentos.vue` los comparten las dos fichas. ⚠️ `ChecklistDocumentos` arma su propio `useForm` y **watchea las claves de los documentos**: al cambiar el tipo, Inertia re-renderiza con props nuevas sin remontar el componente, y sin ese watch el formulario se quedaba con las claves del tipo anterior y los `v-model` reventaban (el bloque desaparecía de la pantalla).
- En proveedores, `notas` no existe: se reusa **`proveedores.observaciones`**, que ya era campo propio del panel. Es la diferencia con `clientes`, donde hubo que llamarla `notas` porque ahí una "observación" es un reclamo. Y ⚠️ **`habilitado` (Sí/No del panel) no es `estado` (A/S/I del ERP)**: la sync pisa el segundo y nunca toca el primero.
- Las claves de documento **se repiten a propósito entre tipos** (`constancia_arca` es el mismo documento en todos): reclasificar un cliente no le borra lo cargado de los documentos que los dos tipos comparten.
- ⚠️ **`clientes.fecha_vencimiento` ya no se carga a mano**: es derivado. Sale del documento marcado `determina_vencimiento` del tipo del cliente y lo escribe `Cliente::recalcularEstadoDocumental()` junto con `documentacion_completa`. La campana de vencimientos (`HandleInertiaRequests`) no cambió: sigue leyendo la misma columna. Un tipo sin documento determinante (Farmacia, Centro Médico, Veterinaria, Institución, Profesional Independiente) **nunca vence**.
- `recalcularEstadoDocumental()` se llama **desde el controller** (en `update()` y en `updateDocumentacion()`), no desde un observer sobre `ClienteDocumento`: el estado depende también de `tipo_cliente`, que se guarda por el otro camino, y un observer sobre el hijo no se enteraría de que cambiar el tipo cambia qué documento manda. Mismo criterio que `ObservacionController::sincronizarNotificados()`.
- **`documentacion_completa` está denormalizado a propósito**: el estado se deriva de config, así que sin esa columna el listado no podría filtrarlo ni ordenarlo en SQL. "Completa" exige todos los obligatorios presentados **y** ninguno vencido; `Cliente::estadoDocumentacion()` devuelve además `faltantes`, `vencidos`, `proximo_vencimiento` y `dias_para_vencer` (el "Control automático" de la planilla) calculados **siempre desde el catálogo cruzado con lo cargado**, nunca desde las filas de `cliente_documentos` solas — así un cambio en el catálogo se refleja sin esperar a que alguien vuelva a guardar.
- Por documento se carga **solo Sí/No + fecha de vencimiento**; no hay adjunto por documento. Los archivos del cliente siguen sueltos en `cliente_attachments`. La fecha se guarda `null` si el documento no vence o no está presentado.
- El checklist se guarda entero de una (`PUT /clientes/{cliente}/documentacion`), que borra las filas de un tipo anterior y rechaza cualquier clave que el tipo no pida. Sin `tipo_cliente` no se puede cargar documentación.
- `clientes.notas` es el "Observaciones" de la planilla. **No se llama `observaciones`**: en este dominio una observación es un reclamo y el cliente ya tiene relación con ellos.
- Hasta el 18/8/2026 el campo de cliente se llamaba `categoria` y era texto libre "hasta que hubiera un catálogo real" (así lo decía su migración). Una migración lo renombra a `tipo_cliente`; no reusar el nombre viejo.
- **El nombre de cada documento se declara una sola vez**, en la clave `documentos` de arriba del config (el "canónico"). Un tipo puede mostrarlo con otra etiqueta (`label` propio: la habilitación del laboratorio de análisis, el certificado del distribuidor), pero la columna del Excel es una sola. Sin esa separación, la misma clave tenía dos nombres y el import no podía saber a cuál corresponde una columna.
- ⚠️ **El mismo documento vence en un tipo y no en otro** (la Habilitación Ministerio vence en Droguería pero no en Farmacia), por eso `vence` es del tipo y no del documento.

### Export e import de clientes por Excel
- `ClienteExportService` / `ClienteImportService` — mismo molde que los de proveedores (PhpSpreadsheet a mano, no hay `laravel-excel`), y el mapeo del import va **por nombre de columna, no por posición**.
- ⚠️ **El archivo que baja el export ES la plantilla del import**: los encabezados son exactamente los que busca el import, así que el circuito exportar → editar en Excel → volver a subir cierra solo, sin plantilla aparte. Cambiar un encabezado de `ClienteExportService` rompe ese circuito.
- El libro tiene **dos hojas**: `Clientes` (los datos) e `Instructivo` (cómo se completa cada columna y la tabla de tipos con su documentación). ⚠️ La de datos tiene que quedar **primera y activa** (`setActiveSheetIndex(0)`): el import lee `getActiveSheet()`, así que si el instructivo quedara activo el import leería el instructivo. Hay un test que sube el archivo exportado tal cual para cubrirlo.
- **El instructivo se genera desde el catálogo, nunca a mano**: un tipo o un documento nuevo aparece ahí solo. Escribirlo como texto fijo garantizaba que se desincronizara del config.
- La hoja de datos lleva **listas desplegables** (tipo de cliente, y SÍ/NO en legajo, habilitado y cada documento). No son cosmética: el import ignora en silencio un valor que no entiende, así que es mejor que Excel no deje escribirlo. `allowBlank` queda en `true` porque la celda vacía es un valor válido — significa "no cambiar".
- El formato es **ancho**: dos columnas por documento del catálogo (el nombre canónico para el SÍ/NO y `"<nombre> - Vto"` para la fecha), no una fila por documento. Es como venían las planillas de Tublood y la única forma de completarlo a mano sin agregar filas.
- **Nunca crea clientes**: la tabla se espeja de RP Sistemas, así que un `numero` que no existe es un error del archivo (advertencia), no un cliente nuevo — un alta acá crearía un registro que la sync no reconocería. Es la diferencia con `ProveedorImportService`, que sí crea porque el Excel es la única fuente del padrón.
- **Una celda vacía no pisa lo cargado** (tipo, notas, y cada documento): es lo que permite subir una planilla parcial y lo que protege lo hecho a mano al reimportar un archivo viejo. Para dar de baja un documento hay que escribir `NO` explícito.
- El tipo se resuelve **antes** que los documentos y en el mismo guardado: una fila que reclasifica y carga papeles del tipo nuevo funciona de una. Los documentos que quedan fuera del tipo nuevo se borran, igual que al guardar el checklist desde la ficha.
- Las columnas calculadas del export (completa / faltante / vencida / próximo vto / días) el import **las ignora**: se recalculan solas.
- Fechas en **dd/mm/aaaa** (o el serial numérico de Excel). `Carbon::parse` leería `03/04/2027` como el 4 de marzo, así que el formato local se prueba primero.
- Advertencias cortadas en 20 con contador del resto, mismo criterio que `ArticuloImportService`: la planilla real tiene miles de filas.
- Permiso propio `clientes.import` (el export usa `clientes.view`), igual que `proveedores.import`.

Los campos `fecha_vencimiento`, `legajo`, `observaciones`, `link_registro`, `proveedor_id` y `proveedor_origen` son **propios del panel** y **no están en la lista de columnas del `upsert()`** — mismo contrato que `clientes.fecha_vencimiento` / `mail_nuevo`. Agregar una columna editable a mano y meterla en esa lista es el error que hay que no cometer.

El motivo: el endpoint exponía ~15 campos y la tabla tiene **142**. `RpSistemasClient::getArticulos()` quedó sin uso pero **no se borró**, para que volver atrás sea cambiar un servicio y nada más.

Por lo mismo `ArticuloImportService` y `ArticuloController::update()` **dejaron de escribirlo**: con tres fuentes sobre la misma columna, gana la última que corre. Junto con él entró `tipo_anmat` (`ID_ARTI_TIPO`: `PM`, `PMV`, `ME`, `A`; etiquetas en `config/articulos.php`).

Medido contra los diez depósitos de `powerbi_stock_vista`, ninguno lo reproduce (el mejor llega a 487 de 748), así que era un cálculo propio del endpoint. Se escribe vacío a propósito en vez de dejar congelado el último número de la API. Pendiente: preguntarle a RP qué resta.

Lo que dejó de venir se marca comparando `synced_at`, que por eso tiene precisión de **microsegundos**. `synced_at IS NULL` marca a los que creó el Excel de Calidad y nunca se desactivan.

Las columnas propias (CUIT, teléfono, mail, localidad, observaciones) se cargan a mano y ningún import las toca.
- ⚠️ **Un proveedor tiene dos puertas de entrada, y por eso `numero` es nullable.** El padrón (`NUM_PROV`/`RAZON`/`DOMICILIO`, vía `ProveedorImportService` con `updateOrCreate` por `numero`) lo trae; el Excel de artículos solo trae la razón social, así que los que entran por ahí quedan **sin número**. El que cierra el círculo es `ProveedorImportService::proveedoresSinNumero()`: antes de dar de alta, busca entre los sin número uno cuya razón social normalizada coincida y lo **adopta** (le completa el `numero`) en vez de crear un segundo registro de la misma empresa — y como adopta el registro existente, los `articulos.proveedor_id` que ya apuntaban ahí siguen sirviendo. Un huérfano adoptado sale del mapa para que dos filas del padrón no se lo peleen, y dos huérfanos que normalizan igual no se adoptan (ponerle el número al que no era es peor que dejarlos sueltos). El índice único sobre `numero` sigue en pie: MySQL y SQLite permiten varios NULL en una columna única.
- **`ArticuloImportService` atiende dos planillas distintas** con un solo código, porque mapea las columnas **por nombre de encabezado y no por posición**: la de Calidad (PM/legajo/vencimiento) y la de proveedores (`cod_articulo`/`descrip_arti`/`proveedor_principal`). Usa las columnas que encuentre e ignora las que falten.
  - El flag `$crearFaltantes` (tilde explícita en el modal, apagada por default) invierte la política de "no crear artículos fantasma" para las planillas que traen códigos que RP todavía no tiene. Sin descripción no crea nada: `descripcion` es NOT NULL. El **mismo flag** da de alta los proveedores cuya razón social no esté en el padrón (sin `numero` — ver arriba), reusando el recién creado en las filas siguientes del mismo archivo para no meter la misma empresa una vez por artículo.

S.A.I.C.` y `PROPATO HNOS S A I C`). Es matcheo **exacto sobre esa forma normalizada, nunca aproximado** — un parecido no alcanza para asignarle un proveedor a un artículo. Dos proveedores que normalizan igual dejan la clave ambigua y no se asigna ninguno. **Ese helper vive en el modelo y no en un servicio a propósito**: lo usan los dos imports (uno para asignar, el otro para adoptar) y si se desincronizaran, un proveedor entraría dos veces.

- ⚠️ `articulos.codigo_proveedor` (string del ERP, **sí** lo pisa la sync en cada corrida) y `articulos.proveedor_id` (FK al padrón local, que la sync **no** toca en el `upsert()`) **no son lo mismo**. En `Admin/Articulos/Edit.vue` el primero está rotulado "Cód. proveedor (ERP)" justamente para que no se confundan.
- **Quién le pone el proveedor a un artículo lo decide [VinculacionProveedores](app/Services/VinculacionProveedores.php)**, en un solo lugar, porque hay cuatro fuentes escribiendo `articulos.proveedor_id` y antes ninguna sabía de la otra. `articulos.proveedor_origen` guarda cuál fue, y la precedencia es `manual` > `erp` > `excel` > `kardex`:
  - `manual` (edición en la ficha) — **nada automático lo pisa**, ni siquiera el ERP.
  - `erp` (`codigo_proveedor` del feed) — pisa `excel` y `kardex`. Es el cambio que habilitó la columna: antes el dato bueno de RP no podía corregir lo que el Excel había adivinado mal.
  - `excel` (import por razón social) — pisa `kardex` y vacíos.
  - `kardex` (`partidas.proveedor_numero`) — solo llena vacíos.
- ⚠️ **`proveedor_origen` no es la columna "Origen" del export**, que dice si el artículo vino de RP o lo creó el Excel de Calidad con "crear faltantes". Son dos preguntas distintas sobre la misma fila.
- ⚠️ **Estado medido de `codigo_proveedor` en RP (2/9/2026)**: 641 de 731 artículos lo tienen **vacío**, y de los 90 cargados **69 son basura** — 32 decimales que parecen costos (`RE-1573` tiene `941.825` con precio de venta `1668.58`) y el resto códigos de artículo (`24001IC04141225X`). Los 21 que son enteros limpios matchean el padrón **al 100%**: cuando RP lo carga bien, entra bien. No repetir este análisis: está en `VinculacionProveedores`.
- **El criterio de "este código sirve" es estar en el padrón, y nada más.** `motivoDeInvalidez()` usa la *forma* del valor solo para explicarle a RP qué pasó ("parece un costo" vs "no existe en el padrón"). Hacer que el reporte tuviera criterio propio (p. ej. "tiene que ser entero") lo dejaba marcando como inválido un código alfanumérico que la vinculación sí usa — lo agarró un test.
- **El kardex es la tercera fuente y funciona hoy**: `COMPRO_PARTIDAS.PROVE_COMPRA` matchea `proveedores.numero` 97/97, y contrastado contra los artículos que ya tenían proveedor coincide en 225 de 231 (97%). Corre al final de `PartidaSyncService::sync()` (04:30) y no dentro de `ArticuloSyncService` (03:00), para usar las partidas recién sincronizadas. ⚠️ **Solo vincula cuando el artículo tiene un único proveedor histórico**: 103 de 823 le compraron a más de uno y elegir sería adivinar.

- El listado de artículos tiene filtro **sin/con proveedor** (heredado por el export, así que la lista de pendientes para RP se baja sola), contador de cuántos faltan, y el reporte de códigos mal cargados.

### Partidas (lotes) — trazabilidad del lote de un reclamo

- **Es la tercera cosa que se lee por la conexión `erp`**, junto con `powerbi_proveedores_vista` y `powerbi_ventas_vista`. No hay una conexión nueva: `COMPRO_PARTIDAS` vive en la misma base `factu_tublood`.
- ⚠️ **Pero es una tabla base del ERP, no una vista habilitada para nosotros.** Las dos vistas de Power BI son un contrato: RP las expuso a propósito. Ésta es interna de su sistema y la leemos porque tenemos SELECT, sin garantía de que no le cambien una columna. Si el sync se rompe de golpe, empezar por ahí; lo correcto a futuro es pedirles una vista.
- ⚠️ **La agregación la hace el ERP, no PHP.** El kardex tiene 390.000 movimientos y agruparlo del lado nuestro obliga a traerlos todos por la red: medido, tarda más de 7 minutos. Agregado en SQL Server son 12.780 filas en ~3 segundos. Tampoco sirven las subqueries correlacionadas (`OUTER APPLY`): la tabla solo tiene índice por `COD_ARTICULO` y el plan se va a minutos.
- ⚠️ **El `GROUP BY` normaliza la clave** (`UPPER(LTRIM(RTRIM(...)))`) y no agrupa por la columna cruda. SQL Server ignora los espacios a la derecha pero **no los de la izquierda**, y su collation acá distingue mayúsculas: `' RE-1573'` y `'RE-1573'` salían como dos grupos que después colisionaban contra el índice único de MySQL, que sí los considera el mismo.
- **Un movimiento no describe la partida entera**: el vencimiento, el proveedor y la ubicación están cargados en unos renglones sí y en otros no, y en una minoría se contradicen (563 partidas con más de un vencimiento, 17 con más de un proveedor, 1.312 con más de una ubicación). La regla es **el movimiento más reciente que tenga el dato cargado**, por columna, resuelta en un solo hash aggregate empaquetando la fecha del movimiento delante del valor y tomando `MAX()` del string.
- ⚠️ **No se guarda ningún saldo de stock.** `SUM(CANTI)` da negativo en 8.041 de las 12.782 partidas y positivo en solo 468: la tabla registra consumos contra la partida pero no todos los ingresos, así que ese número no es una existencia y mostrarlo mentiría.
- ⚠️ **La clave es (artículo, partida), no la partida sola**: 885 códigos de lote se repiten entre artículos distintos. `Partida::adjuntarAProductos()` desempata con el `codigo` del producto reclamado y, si el producto no trae código y el lote es ambiguo, **no atribuye ninguna** — mandar a revisar el artículo equivocado es peor que no atribuir.
- La atribución va **en el controller y no en un eager load** porque `belongsTo` no sabe de claves compuestas: `ObservacionController::show()` llama a `Partida::adjuntarAProductos()`, que resuelve todos los productos en una query y cuelga el resultado con `setRelation('partida', ...)`. Se lee **en vivo del padrón**, nunca de una copia guardada en la observación — mismo criterio que el proveedor del artículo. ⚠️ La relación se setea **siempre**, aunque sea en `null`: si no, Inertia no manda la clave y el front recibe `undefined` en vez de "no se pudo atribuir".
- `Partida::normalizarCodigo()` solo pasa a mayúscula y recorta espacios. A diferencia de `Proveedor::normalizarRazonSocial()`, **no** saca guiones ni puntos: `20260522-582` y `20260522582` son lotes potencialmente distintos.
- En el front, `Show.vue` lo muestra en un bloque **aparte** de la tabla de productos (`lib/partidas.ts`, mismo molde que `lib/productos.ts`): arriba está lo que declaró el cliente, abajo lo que sabe el ERP. Mezclarlos escondía la discrepancia de vencimiento, que es justamente el dato que importa — y por eso hay un badge `≠ declarado`.
- Cobertura real del padrón: 11.639 de 12.780 partidas con vencimiento, 6.787 con proveedor (los 97 números distintos matchean `proveedores.numero`, 0 huérfanos), 2.891 con ubicación. 111 códigos de artículo del ERP no están en el catálogo local.
- `partidas:sync` (job + comando, con `--sync` para modo síncrono), agendado `dailyAt('04:30')` con el mismo guard `->when($erpConfigurado)` que proveedores y ventas.
- **Listado en `/partidas`** (`Admin\PartidaController` + `Pages/Admin/Partidas/Index.vue`), permisos propios `partidas.view` / `partidas.sync`, mismo molde que Ventas: solo lectura, buscador con debounce, filtros que recargan al toque, tabla en desktop y `TableCard` en mobile. Filtra por proveedor, por estado de vencimiento y busca por lote, código de artículo, descripción o razón social.
- ⚠️ **El buscador normaliza el lote a mayúsculas pero no los demás campos**: el lote es una clave que se cruza contra lo que tipeó un cliente (por eso `atdec24` encuentra `ATDEC24090046`), mientras que artículo y proveedor son texto libre que el usuario está leyendo, no cruzando.
- ⚠️ **`sin_vencimiento` no es "no vence"**: son las 1.141 partidas donde ningún movimiento del kardex trae `FECHA_VENCI`. Es un dato faltante del ERP, no una propiedad del producto — por eso es un filtro propio y en la tabla sale en gris, no en verde.
- El select de proveedores ofrece **solo los que tienen partidas** (96 de los 1.849 del padrón): con el padrón entero sería inusable.
- Las partidas cuyo `codigo_articulo` no está en el catálogo local se listan igual, con la leyenda "fuera del catálogo". No se filtran: son partidas reales del ERP, y esconderlas ocultaría justamente los casos que hay que revisar.

### Lotes despachados por comprobante (`venta_partidas`)

Qué lote salió en cada renglón de venta. Sale del **mismo kardex** que `partidas` (`COMPRO_PARTIDAS`) pero a otro grano: `partidas` agrega a una fila por artículo+lote y descarta el comprobante, así que no puede responder "a quién le despaché este lote". Cierra la trazabilidad en las dos direcciones y es lo que hace falta para un recall.

- ⚠️ **El número de remito NO identifica un remito.** `NUM = 8500` devuelve tres remitos distintos (`VR6/8500`, `VR8/8500`, `VRM/8500`), de facturas diferentes: **7.395 de 25.320 números (29%) están repetidos entre series**. Como `ventas.remito_nro` es un entero pelado sin la serie, joinear por remito daría el lote equivocado casi un tercio de las veces.
- **El join va por el comprobante, que sí es único**: `COMPRO_PARTIDAS.TIPO = ventas.cod_comprobante` + `NUM` = los 8 dígitos finales de `ventas.compro_nro`. Hay un índice `(TIPO, NUM, RENGLON, SECUEN)` que lo cubre.
- ⚠️ **`compro_nro` se guarda reconstruido** como `sprintf('%s-%08d', TIPO, NUM)` para joinear por una sola columna. Siempre 8 dígitos: verificado sobre los 60.781 registros de `ventas`.
- ⚠️ **No partir `compro_nro` por el guion**: `F-A-00001857` partido por `-` da `F`. El tipo autoritativo es `cod_comprobante`, que nunca es null.
- ⚠️ **`PRECE_*` no siempre es un remito.** Es "el documento que precedió al movimiento", y en el 39% de las filas es un movimiento de stock (`STO`/`STI`): coincide con `ventas.remito_nro` en **0 de 158** casos. Solo las series `VR*` son remitos, y ahí la coincidencia es de **14.486 sobre 14.486 (100%)**. Por eso `VentaPartida::SERIES_DE_REMITO` filtra, y el accesor `remito` devuelve `null` fuera de esas series para que la pantalla caiga al `remito_nro` que ya trae `ventas`.
- ⚠️ **El `GROUP BY` normaliza artículo y lote** (`UPPER(LTRIM(RTRIM(...)))`), por el mismo motivo que en `PartidaSyncService`: sin eso el índice único de MySQL colisiona con lo que SQL Server considera dos grupos.
- **Cobertura 88%**: 53.347 de 60.781 renglones de venta resuelven a un lote. El 11-12% restante son artículos sin trazabilidad (servicios, ajustes de cambio) — vacío es un resultado normal, no un error, y por eso `adjuntarAVentas()` setea la relación **siempre**, aunque sea vacía.
- **96,5% de los renglones salen de un solo lote**; 5.105 salen de dos, con cola larga hasta 101. Por eso es tabla hija y no una columna en `ventas`.
- La atribución al listado va por `VentaPartida::adjuntarAVentas()` (clave compuesta `compro_nro` + `articulo`, una query por página), mismo patrón que `Partida::adjuntarAProductos()`.
- **Ficha de partida** en `/partidas/{partida}` con sus despachos paginados. El cliente sale de `ventas` por LEFT JOIN: ⚠️ `ventas` **solo cubre desde 2024-08** y el kardex llega a 2016, así que los despachos viejos muestran comprobante y cantidad pero no cliente — se dice por qué en vez de poner un guion.
- El filtro por lote del listado de Ventas es **propio y no parte de `Venta::scopeBuscar()`**: ese scope cruza dos términos entre sí y meterle el lote enturbiaría esa semántica.
- `venta-partidas:sync` (job + comando, con `--sync`), agendado `dailyAt('04:15')` — después de `ventas:sync` — con el mismo guard `->when($erpConfigurado)`. Son ~166.400 filas, refresh completo.

**Tres tablas espejo, refresh completo** (`compras:sync`, job + comando con `--sync`, agendado `dailyAt('05:00')` — después de `ventas:sync` de las 04:00 para que el tablero abra con las ventas del día):

- `compras_articulos` ← `ARTICULOS` (5.229 filas). ⚠️ Es una **tabla aparte de `articulos`, no un reemplazo**: `articulos` (734 filas) viene de la API HTTP y es el catálogo "vendible" que usan observaciones, el portal público y la vinculación de proveedores; Compras necesita el catálogo completo, discontinuados incluidos. El local es subconjunto exacto del ERP (734 de 734 matchean), así que unificarlas es posible más adelante — cambiaría el buscador del portal y los contadores del listado de Artículos.
- `compras_ordenes_pendientes` ← `powerbi_ordenescompra_pend_vista`, **con `CANT_PEND > 0`**. ⚠️ La vista es histórica: 21.502 renglones de los cuales **solo 228 tienen saldo** (hay OC entregadas desde 2016). El filtro es la regla, no una optimización.
- `compras_pedidos_pendientes` ← `powerbi_pedidos_vista`, con `cant_pend > 0` (35.643 de 122.752). ⚠️ **No** se filtra por la regla de reserva: ver abajo.

Las **ventas salen de la tabla `ventas` que ya existe**, sin sync nueva.

⚠️ **`ARTICULOS` es una tabla base del ERP, no una vista `powerbi_*`.** Mismo riesgo que `COMPRO_PARTIDAS`: la leemos porque tenemos SELECT, sin contrato. Si el sync se rompe de golpe, empezar por ahí.

⚠️ **`compras_articulos.codigo` va con colación `utf8mb4_bin`** (solo en MySQL; SQLite ya compara binario y no conoce esa colación). `utf8mb4_unicode_ci` ignora acentos y colapsaría dos códigos que el ERP considera distintos, y la sync perdería artículos en silencio. Hoy pasa con `CODIGO` vs `CÓDIGO` — dos filas de encabezado de planilla que alguien importó al ERP.

**El cálculo vive en el cliente.** `app/Services/Compras/ReposicionService.php` arma el dataset (unificación por GTIN, cruce con ventas/OC/reservas) y lo manda **entero** en las props: ~1 MB, ~185 KB gzip. `resources/js/lib/compras.ts` hace filtros, orden, Pareto y las fórmulas. Es la única pantalla del panel que no pagina en el servidor, y es a propósito: los KPIs y la fila de TOTAL se calculan sobre todo el conjunto filtrado y el Pareto se recalcula sobre ese mismo conjunto, así que el servidor recorrería los 4.800 grupos igual, con un roundtrip por cada click de ordenamiento. Por lo mismo **el export es CSV generado en el navegador** (`lib/comprasCsv.ts`) y no un `.xlsx` con PhpSpreadsheet como el resto: un export server-side obligaría a duplicar en PHP filtros, orden y fórmulas, que es donde se desincronizarían de lo que se ve.

⚠️ **`deploy/nginx-sgo.conf` declara `gzip on` por esta pantalla.** Es la respuesta más pesada de la app por lejos (1,1 MB sin comprimir). Ubuntu ya trae gzip activo, pero que esta pantalla sea usable no puede depender de un default de la distro.

El dataset usa **claves de una letra** (`n`, `c`, `u`, `i[]{c,d,a,u,k,s,r,o,v,m}`): con nombres largos el payload pasa de 1 MB a más de 2. Y ⚠️ **cada grupo lleva un `id` estable**, que es lo que va en `:key` y lo que indexa las filas desplegadas: **el nombre no sirve como clave**, hay 73 descripciones repetidas entre 166 artículos distintos sin GTIN, y usarlo hacía que desplegar un producto desplegara otro.

**Las reglas de negocio, y por qué son así:**

- **Se MULTIPLICA por el envase, nunca se divide.** El ERP cuenta en envases y `CODIGO_REFERENCIA` dice cuántas unidades trae cada uno; el tablero entero está en unidades. Vacío o 0 valen 1 y la pantalla muestra "–", no "1". ⚠️ **El envase es por ARTÍCULO, no por grupo**: un grupo puede mezclar un x500 con un x150 (hoy 8 grupos), cada uno convierte con el suyo y el grupo suma en unidades; la columna muestra "varios". RP está completando el dato — eran 13 artículos el 8/9/2026 y 33 el 10/9.
- **La categoría también es por artículo** (`AGRU_1`): un grupo puede mezclar DISTRIBUCIÓN e IMPORTACIÓN (hoy 33), muestra las dos y aparece si **cualquiera** está filtrada.
- **Unificación multimarca por GTIN.** ⚠️ `GTIN` **no es un código de barras**: es una clasificación de texto cargada a mano ("AGUJA 25/6 (23GX1)"), llena de comodines — "NO APLICA" (559), "N/A" (27), "0" (27), más typos. Se descartan **por patrón y no por lista fija** (`config('compras.gtin_comodin')`) porque van a aparecer typos nuevos, y el patrón se aplica al armar el dataset y no al sincronizar, así que corregirlo es editar config sin esperar la sync del día siguiente.
- **Notas de crédito: ya vienen en negativo** del ERP (CEA/CEB/CA1/CNN/CEE/CNA) y se suman **tal cual**. Negarlas las pasa a positivo y suman ventas en vez de restarlas — ese error infló la facturación un 35% en el prototipo.
- **Stock negativo = error del ERP** (hoy 15 artículos, el peor en −4.296.450). Viaja **crudo** desde el servidor y lo cuenta como 0 la pantalla, que además marca el producto con ⚠. Corregirlo en la sync escondería el error de carga. Sin esto, ordenar por "cantidad a comprar" llena el tope de basura.
- **`SIN_STOCK = 'S'`** (41 artículos) van a una categoría propia SERVICIOS y quedan fuera del cálculo salvo que se los pida. Un grupo se excluye solo si **todos** sus artículos lo son.
- **Cobertura: TRES estados, no dos.** Un producto sin ventas en el período **no es** un "NO cubre": es SIN VENTA y muestra "–", nunca 0. En el prototipo los "NO" bajaron de 342 a 166 reales al separarlos.
- **Pareto ABC sobre `sub_total`** (el total de línea, no el precio unitario), recalculado **sobre el conjunto ya filtrado**: si se filtra una categoría, da el 80/20 de esa categoría. El producto que **cruza** el 80% va en A. Sin facturación queda sin clase y afuera de los dos filtros.

⚠️ **`Reservado` NO está conciliado con el ERP.** La regla (`reser='S'` + depósito "Deposito unico" + `cant_pend>0`) vive en `config('compras.reserva')` y no hardcodeada justamente por eso: el campo que decide la reserva **no está en la vista**, las líneas que el ERP cuenta y las que no son idénticas en `reser`, depósito y `estado`. Por eso `compras_pedidos_pendientes` guarda **todos** los renglones con saldo y no solo los reservados — filtrar en la sync congelaría la regla. Pista medida: de las 511 líneas que hoy cuentan, **160 en estado `ADMINISTRACION` explican 122.928 de las 170.990 unidades (72%)**; si al conciliar sobra ese volumen, agregarlo a `estados_excluidos`. La pantalla lo avisa mientras `estados_excluidos` esté vacío.

⚠️ **`UM_COMPRA` es inservible**: 64% NULL y el resto es ruido (`1`, `36,`, `5/1`, `GRS`). Se guarda para poder auditarlo, pero el cálculo **asume que `cant_pend` viene en la misma unidad que el stock**. Es el supuesto más frágil del módulo y el primero a validar contra la pantalla del ERP.

**Equivalencia con el prototipo**: `lib/compras.ts` se verificó contra la implementación original del HTML corriendo las dos sobre el mismo dataset — 18 escenarios de filtros, 14 campos por fila y 6 criterios de orden, sin una sola diferencia. Cualquier cambio en las fórmulas debería repetir esa comparación antes que confiar en los tests unitarios.

Campos que siguen siendo **únicos por observación** (no por producto): `institucion`, `provincia`, `equipamiento`, `ejecutivo_cuenta`.

Se lee **en vivo del padrón**, nunca de una copia guardada en la observación: completarle el proveedor a un artículo reencuadra también los casos ya cargados. El eager load está centralizado en `ObservacionController::EAGER_PRODUCTOS` — ⚠️ `proveedor_id` **tiene que estar** en la lista de columnas del artículo o el `belongsTo` anidado devuelve `null` sin avisar.

Los dos "sin dato" se distinguen a propósito (`resources/js/lib/productos.ts`, compartido por las dos vistas): **"Código sin artículo"** se arregla en la observación, **"Artículo sin proveedor"** en el padrón de artículos. El **portal público no lo muestra**: es la pantalla del cliente y de quién compramos es interno (`articulos.buscar`, que es público, sigue devolviendo solo código y descripción).
- El Dashboard tiene **"Proveedores con más fallas"**, que cuenta **renglones de producto y no observaciones** (un caso con tres artículos del mismo proveedor le suma tres), excluye las canceladas (caso anulado o duplicado no es falla del proveedor) y **reporta aparte los renglones sin proveedor atribuible** — sin ese número el ranking mentiría por omisión, porque hoy 667 de los 4200 artículos no tienen proveedor cargado. Cada barra lleva al listado filtrado por `proveedor_id`.

Hasta el 25/7/2026 existían dos tablas separadas (`sectors` y `areas`, esta última "creada sola" al importar el Excel); se unificaron porque los datos reales mostraban que eran la misma lista con distinta nomenclatura, y la separación bloqueaba filtrar "usuarios de tal sector" — prerrequisito de la clasificación exclusiva de Calidad y de la derivación entre sectores.

### Tope de observaciones abiertas por sector (`sectores:tope`)

Desde el 1/10/2026 cada sector puede tener un **tope de observaciones abiertas** (`sectors.tope_observaciones`, editable desde el ABM). Al superarlo, `sectores:tope` (agendado **horario**) le avisa al gerente del sector por campana y mail.

Es una pregunta distinta de la de `observaciones:alertas`: aquél escala **casos vencidos de a uno** —o sea, cuando el incumplimiento ya pasó—, éste mira la **carga del área** y suena antes, cuando todavía se puede repartir trabajo.

- ⚠️ **El umbral es estricto**: un tope de 5 se supera recién con 6. "Aguanta 5" significa que 5 está bien. Hay un test en los dos bordes.
- ⚠️ **`null` = sin tope, no avisa nunca.** Es el estado inicial de los diez, y por eso la función no molesta a nadie hasta que alguien la use.
- ⚠️ **Se cuenta por `observations.sector_id`** (a dónde se derivó el caso), **no** por el sector del responsable, que es de donde sale el plazo de vencimiento. El código ya usaba las dos nociones en paralelo. Las observaciones **sin sector no se cuentan**: no son de nadie y nadie puede resolverlas.
- ⚠️ **`tope_avisado_at` es la marca de idempotencia**, y se limpia al bajar del tope. Sin ese "se limpia", el sector avisaría una sola vez en su vida. Mismo mecanismo que `verificacion_avisada_at` en `nc:recordatorios`. **Tiene que estar en `$fillable`** o `update()` la descarta en silencio y el aviso sale en cada corrida — es el bug que apareció al escribir esto.
- **Quién es "el gerente del sector"** se deriva, porque no existe como campo: la **unión** de los `gerente_id` de la gente del sector y de los `es_gerente` cargados en él, con caída a los **super-admin** si no hay ninguno. Un aviso no puede perderse porque falte cargar una jerarquía — mismo criterio que el alta del portal.
- ⓘ El aviso enlaza al listado de **abiertas** y no al del sector: `observaciones.index` todavía **no tiene filtro por sector**.

⚠️ **El vencimiento sale del sector del *responsable*, no de la observación.** El reloj lo calcula `ObservacionObserver` con `$responsable->sector->dias_gestion`. `observations.sector_id` es un dato propio del caso (a qué sector se derivó, para reportes y para filtrar tipos de incidencia) y no mueve el SLA por sí solo — cambia si cambia el responsable, no al revés.

El **portal público deriva el sector del tipo**: el cliente elige el tipo y `TaxonomiaIncidencias::sectorDeTipo()` resuelve a cuál pertenece (los dos tipos externos están declarados bajo `garantia_calidad`). Si faltara el registro en `sectors`, queda en `null` y el reclamo se guarda igual — el portal es público y nunca puede perder un reclamo.

Al crear una observación externa, `Portal\ObservacionController::avisar()` manda dos avisos **fuera de la transacción**: acuse de recibo al cliente y aviso a quien lo va a clasificar.

⚠️ **El destinatario interno sale del `tipo`, no del sector.** Los dos tipos externos cuelgan del mismo sector (`garantia_calidad`), así que el sector no alcanza para repartirlos entre las personas del equipo. El mapeo vive en `config('incidencias.roles_por_tipo')` (`falla_producto` → `calidad_producto`, `disconformidad_servicio` → `calidad_servicio`) y lo lee `TaxonomiaIncidencias::rolDeTipo()`. Agregar un tipo externo nuevo es solo config. Tres cosas no negociables ahí:
- **Si nadie tiene el rol, cae al criterio viejo** (unión de gente del sector de la observación + gente con el rol `garantia_calidad`). El portal es público: un reclamo no puede quedar sin que se entere nadie porque falte configurar un rol.
- Se busca con `whereHas('roles', ...)`, **no** con el scope `User::role(...)` de Spatie: ese scope **tira `RoleDoesNotExist`** si el rol no está creado, y eso sería un 500 en un endpoint público (lo agarró un test).
- Todo va dentro de un `try/catch` que loguea: para cuando corre, el reclamo ya está guardado, así que un fallo al avisar no puede devolverle un error al cliente y hacerle creer que no se cargó.

Si el `contacto_numero_cliente` matchea un cliente local, el mail que tipeó el cliente se guarda en **`clientes.mail_nuevo`** (no en `mail`, que lo pisa la sincronización con RP cada 5 minutos — ver la lista de columnas del `upsert()`). Es editable a mano desde `Admin/Clientes/Edit.vue`.

### Estructura de usuarios y motor de alertas
- **Jerarquía** — `users` tiene `sector_id`, `supervisor_id` (a quién se escala), `gerente_id` (aviso final + último escalón) y `es_gerente`. `User::cadenaEscalamiento()` sube por `supervisor_id` con guarda de visitados; `User::generariaCiclo($id)` es el chequeo anti-círculo que usan **tanto** el formulario (`UserController::reglas()`) como el import.
- **Import de Excel** ([app/Services/UserImportService.php](app/Services/UserImportService.php)) — 7 columnas por posición (Nombre, Apellido, Mail, Sector original, Supervisor, Gerente, Tiempo de gestión), upsert por email. Va en **dos pasadas** porque el archivo referencia supervisores que aparecen en filas posteriores: la primera crea/actualiza usuarios y resuelve sectores, la segunda resuelve los nombres. `"si"` en la columna Supervisor marca a los gerentes. **Las columnas vacías no pisan lo cargado**, así que un archivo viejo de 3 columnas sigue funcionando. Los problemas (nombre inexistente/ambiguo, ciclo, plazos en conflicto, sector fuera del catálogo) salen como **advertencias** en el flash `error`, no abortan el import.
- **Reloj de gestión** — `observations.responsable_asignado_at` / `vence_at` / `alerta_nivel` los setea [app/Observers/ObservacionObserver.php](app/Observers/ObservacionObserver.php) (enganchado con `#[ObservedBy]`), **no** los controllers: el responsable se asigna desde tres lugares distintos y así hay un solo punto de verdad. Arranca al asignar responsable (no al crear), dura `sector.dias_gestion` **días hábiles** (`addWeekdays()`, sin feriados argentinos) y se reinicia al reasignar. Sin sector o sin plazo, `vence_at` queda `null` y esa observación nunca alerta.
- **Escalamiento** — `observaciones:alertas` (agendado `->hourly()`): nivel 0→1 avisa a responsable + supervisor; 1→2 escala al gerente + supervisor recién cuando pasó **otro** plazo igual. `alerta_nivel` lo hace idempotente. Al pasar a un estado de `config('incidencias.estados_finales')` (hoy solo `cerrada`) el observer manda el **aviso final** al gerente.
- **Estados** — el catálogo es `Observacion::ESTADOS`. Hasta el 31/7/2026 existía además `resuelta`, que se unificó en `cerrada` (una migración remapea las filas viejas): eran la misma idea con dos nombres, y como solo `cerrada` está en `estados_finales`, marcar un caso "resuelto" lo dejaba con el reloj corriendo y sin aviso final. **`cancelada` no se unificó y no hay que unificarla**: un caso anulado o duplicado no es trabajo terminado, por eso queda fuera del stat "Cerradas" y del gráfico por estado del Dashboard. ⚠️ Desde el 28/9/2026 hay además `derivada_nc` ("Derivada a No Conformidad"), que **no es** el `derivada` de la derivación entre sectores — ver la sección de No Conformidades.
- **Paso a crítica** — `ObservacionObserver::avisarSiPasoACritica()` avisa al responsable cuando la prioridad **entra** en `critica` (no ante cualquier cambio: bajar de crítica no interrumpe a nadie). No avisa si en el mismo guardado cambió el responsable — el aviso de asignación ya viaja con la prioridad nueva y sale en rojo — ni a quien hizo el cambio (`auth()->id()`), porque avisarle a alguien de su propia acción es ruido.
- **Notificaciones** — `app/Notifications/Observacion*Notification.php` heredan de `ObservacionNotification` (canales `database` + `mail`, e **implementan `ShouldQueue`**: cada mail es una llamada HTTP a Resend, así que no puede colgar la request). El canal `database` alimenta la campana vía `HandleInertiaRequests` → `notificaciones.alertas`. La única que **no** hereda de la base es `ObservacionRecibidaClienteNotification`: su destinatario es un mail suelto (`Notification::route('mail', ...)`), no un `User`, así que no tiene canal `database` ni `$notifiable->name`. ⚠️ **Los dos canales no van por el mismo lado**: `viaConnections()` manda `database` a la conexión `sync`, así que la fila se escribe en el acto (es un INSERT local), y solo `mail` queda encolado — que es la llamada HTTP a Resend y lo único que justifica la cola. Gracias a eso la campana y el modal de reclamos nuevos funcionan **aunque no haya un worker corriendo**; lo que sí se acumula sin worker son los mails. Con `QUEUE_CONNECTION=database` y la app servida por el vhost de Laragon no hay worker: hay que correr `php artisan queue:work` aparte (o `composer run dev`, que ya lo levanta), y en prod hace falta un supervisor/cron. Si alguna vez se agrega un canal nuevo, decidir explícitamente de qué lado va.
- **Aviso de alta a los super-admin** (`ObservacionCreadaNotification`) — cada observación que entra, venga del portal o del panel, le avisa a **todos** los super-admin por campana + mail. Lo dispara `ObservacionObserver::avisarALosSuperAdmin()` desde `created()` y no los controllers, porque hay tres caminos de alta. Tres cosas para no romper:
  - **Es una clase propia y no un reuso de `ObservacionExternaRecibidaNotification`**: `HandleInertiaRequests` excluye ese tipo de `notificaciones.alertas` (para no duplicar el bloque "Sin clasificar"), y una interna nace `clasificada`, o sea que nunca está en ese bloque — reusarla dejaría el aviso escrito en la base **sin ningún lugar donde mostrarse**. Además `externasPendientes()` arrastraría al super-admin al modal de quien clasifica.
  - **No le avisa tres veces a la misma persona**: quedan afuera quien cargó el caso (`created_by`, con `auth()->id()` de red), el responsable asignado (ya recibe Asignada o ExternaRecibida) y, en las externas, quien atiende ese tipo por rol. **No** se replica el *fallback* de `Portal\ObservacionController::avisar()`: duplicar esa regla acá la condenaba a desincronizarse.
  - ⚠️ Corre **dentro de la transacción** del alta del portal, que es pública: va todo en un `try/catch` que loguea, y el filtro es `whereHas('roles', ...)` y **nunca** el scope `User::role(...)` de Spatie (tira `RoleDoesNotExist` si el rol no existe). ⚠️ Y la bandera `omitirAvisoDeAsignacion` apaga **solo** el aviso de asignación — hasta el 21/9/2026 hacía `return` y cortaba el método entero.
  - Si el volumen de mails molesta, la salida limpia es cambiar el rol por un permiso propio (`observaciones.notificar_altas`): se puede dar y sacar sin dar god-mode.
- **Los avisos de vencimiento dicen de quién es el caso** (trait `Notifications\Concerns\DetallaElAtraso`, compartido por `ObservacionVencida` y `ObservacionEscalada`). Hasta el 21/9/2026 el supervisor leía "la observación 0012-26 venció" y tenía que abrir el caso para saber a quién preguntarle. Ahora el asunto, el cuerpo y la campana llevan nombre, sector, mail de contacto, fecha de vencimiento y días **hábiles** de atraso. Cuatro decisiones:
  - Se agrega con el hook `detalles($notifiable)` de la clase base (vacío por defecto) y **no** sobreescribiendo `toMail()`: ese método concentra el prefijo de prioridad crítica, el `replyTo` del sector y el botón, escritos una sola vez.
  - ⚠️ **El nombre NO va en `mensaje()`**, porque ese texto es también la primera línea del mail y el aviso de nivel 1 le llega **al propio responsable**: leer el nombre de uno en tercera persona abajo de "Hola <uno>," es raro. Lo inyecta `toArray()` (para la campana) y lo pone `detalles()` solo para quien **no** es el responsable, que en cambio lee "está a tu cargo".
  - El texto **no acusa a nadie** ("está a cargo de", nunca "no dio respuesta"): el atraso puede no ser culpa del responsable, y el mismo mail le llega a él.
  - `responsable()` usa `loadMissing()` y no confía en el eager load del comando: solo el canal `mail` va encolado, así que `toMail()` corre en el worker sobre una notificación deserializada.
- **Reclamos sin clasificar** — dos capas independientes, ambas en `HandleInertiaRequests`, **recortadas al tipo que atiende cada uno** (`User::tiposDeReclamoQueAtiende()`): quien tiene `calidad_producto` ve solo las fallas de producto y quien tiene `calidad_servicio` solo las disconformidades. Quien es de Garantía de Calidad "a secas" (rol `garantia_calidad` **o** sector homónimo — `User::esDeCalidad()`) sigue viendo **todos** los tipos: ese método devuelve `null` para ese caso, que significa "no recortar". Es a propósito, para no perder la vista global mientras se termina de repartir el equipo.
  - **Campana → "Sin clasificar"** (`notificaciones.sinClasificar`): consulta viva `Observacion::where('estado', 'pendiente_clasificacion')`, no la tabla de notificaciones. Es la fuente de verdad — se autolimpia sola en cuanto alguien clasifica el caso (desde ahí mismo o desde el modal de edición del listado) y no puede quedar desincronizada ni apuntar a una observación borrada.
  - **Modal "Entró un reclamo nuevo"** (`notificaciones.externas`): el *subconjunto* de lo de arriba de los que a este usuario le avisaron — se calcula filtrando `sinClasificar` contra las `ObservacionExternaRecibidaNotification` de ese usuario (leídas o no; ver más abajo), no con una consulta aparte, así el popup nunca puede ofrecer algo ya clasificado o inexistente. El mismo modal en `AppLayout.vue` suma otros dos bloques igual de vivos — `asignadas` (casos abiertos a cargo del usuario) y `seguimiento` (casos donde lo sumaron como notificado) — que se apagan solos al llegar a un estado fuera de `ESTADOS_ABIERTOS`. **Insiste hasta que se resuelve el trabajo real** (clasificar el reclamo, o cerrar/cancelar el caso): cerrar el modal **no** marca nada en el servidor, solo descarta esos IDs en `avisosVistos`, un `Set` a nivel de módulo declarado en el propio `AppLayout.vue` (mismo patrón que `modalesAbiertos` en `Components/Modal.vue`) — dura toda la carga de la app (sobrevive a la navegación de Inertia, porque `AppLayout` se remonta en cada una) y se reinicia con login, F5 o pestaña nueva, momento en el que el modal vuelve a insistir. Se refresca con `usePoll(60000, { only: ['notificaciones'] })`, así que puede aparecer en cualquier pantalla mientras la persona ya está trabajando: se abstiene si la pantalla es un formulario (`page.component` matchea `Crear|Create|Edit|Nuevo`) o si hay otro modal abierto (contador a nivel de módulo `modalesAbiertos` en `Components/Modal.vue`).

  `alertas` (las de vencimiento/escalamiento) excluye el tipo `ObservacionExternaRecibidaNotification` para no duplicar lo que ya muestra "Sin clasificar", y por la misma razón `NotificacionController::marcarLeidas()` (el botón "Marcar leídas" de ese bloque) no toca esos avisos — son dos mecanismos independientes.

  En el fallback (cuando nadie tiene el rol del tipo), `Portal\ObservacionController::avisar()` notifica a la **unión** de sector y rol `garantia_calidad`, y no al sector con el rol de fallback: quien tiene el rol pero está cargado en otro sector también tiene que ver el aviso.
- **Sectores** — ABM mínimo en `Admin/Sectores/Index.vue` + `Admin\SectorController`, gateado con los permisos **`users.view`/`users.edit`** (no tiene permisos propios: es parte de la estructura de usuarios). Existe para corregir `dias_gestion` sin reimportar el Excel — **no** amplía el catálogo fijo de sectores (ver arriba). `SectorController::update()` **no recalcula el slug** al renombrar, porque es la clave con la que el import y `config/incidencias.php` reconocen el sector.

### Bajas y cierres (`/bajas`) — el archivo de casos terminados
Muestra las observaciones **cerradas**, **canceladas** y **borradas** (soft delete). Las cerradas se sumaron el 21/9/2026; antes la pantalla era solo de bajas.
- ⚠️ **Quién cerró el caso sale de la columna propia `observations.cerrada_por`, no de la bitácora.** Mismo motivo por el que existe `cerrada_at`: `observation_history` guarda la **etiqueta legible** del estado y no el slug, así que no es consultable de forma confiable (el estado `resuelta`, unificado en julio, dejó entradas que dicen `'Resuelta'`). La escribe `ObservacionObserver::marcarCierre()` en el mismo UPDATE que el estado, y vuelve a `null` al reabrir.
- ⚠️ **La relación se llama `cerradaPorUsuario()` y no `cerradaPor()`**: Eloquent serializaría esta última como `cerrada_por`, que es el nombre de la columna `int`, y la clave del JSON quedaría con el objeto o con el id según el orden de serialización.

Ampliarlo (bajarlo a `observaciones.view` o darle permiso propio) expone el motivo y el autor de cada baja, así que es una decisión aparte que además **toca `deploy.sh`**, que reseedea permisos.
- El nombre "Bajas" ya no describe del todo el contenido. Se ajustó el copy ("Bajas y cierres") y se dejó la URL: renombrar la sección completa a "Archivo" (URL, ruta, carpeta, menú, test — como se hizo con Auditoría → Bitácora) es un cambio aparte.

### No perder los filtros ni la página al escribir
Los filtros, el orden y `?page=` viven en la URL del listado (todos los paginadores usan `->withQueryString()`), pero hasta el 21/9/2026 el redirect posterior a cualquier escritura los descartaba: editás un registro de la página 3 y volvés a la 1 sin filtros. Hay **dos mecanismos según de dónde salga la acción**, y elegir mal es el error fácil:

- **La acción sale del propio listado** (modal de edición o de borrado, Importar, Sincronizar) → **`back(fallback: route('x.index'))`**. `UrlGenerator::previous()` lee el header **Referer**, que con Inertia (`pushState`) es la URL filtrada. Cero frontend.
  - ⚠️ **El `fallback` no es decorativo.** En un test no hay Referer ni sesión previa y `back()` pelado devuelve a `/`. Con él, producción gana por Referer y los tests por fallback — por eso las ~30 assertions que ya existían no hubo que tocarlas.
  - ⚠️ **La regla NO es "un `store()` nunca usa `back()`"**: `SectorController::store()` sí lo usa, porque su alta es un modal sobre el listado. Lo que manda es de dónde sale la acción, no si crea o edita. Los `store()` que vienen de una página Create (Users, Roles, Observaciones) se quedan con `redirect()->route('x.index')`: devolver al formulario de alta sería peor, y el registro recién creado probablemente no entre en el filtro que había.
  - ⚠️ **Borrar la última fila de la última página** ahora deja una página vacía (antes caías en la 1). Es el precio de conservar el paginado; se ve el empty-state y el link "anterior" funciona.
- **Hay una ficha `Edit.vue` separada** (Clientes, Users, Artículos, Proveedores, Roles) → el parámetro **`volver`**, porque ahí la URL filtrada se pierde **ya al entrar**: el link "Editar" es otra URL. Backend: trait [VuelveAlListado](app/Http/Controllers/Concerns/VuelveAlListado.php) (`$this->alListado($request, 'x.index')`). Frontend: [useVolverAlListado.ts](resources/js/composables/useVolverAlListado.ts), con sus dos mitades — `useIrALaFicha()` arma el link del listado y `useVolverAlListado(ruta)` da el `urlListado` del "← Volver" y el `aGuardar()` del submit.
  - `volver` es **una cadena opaca**: la query del listado tal cual, codificada y decodificada exactamente una vez por capa. Viaja en la **URL del PUT** y no como campo del form, así no ensucia el `useForm` ni `form.isDirty`.
  - ⚠️ **No hay open redirect**: la URL base sale siempre de `route()` y `volver` se **reparsea** con `parse_str()`, nunca se concatena crudo (concatenar dejaría pasar saltos de línea al header `Location` y un `#` que corte la URL). Lo peor que se logra es ensuciar la query de nuestro propio listado, que la ignora. Hay un test que lo fija.
  - ⚠️ Sirve solo para rutas **sin parámetros de ruta**; y `parse_str()` convierte `.` y espacios en `_` en las claves (ningún filtro del panel los usa hoy).
  - Se descartó guardar la URL en **sesión**: es menos código, pero dos pestañas comparten la clave y la segunda ficha le pisa la vuelta a la primera sin avisar — y la ficha necesita el dato igual para dibujar su "← Volver".
  - ⚠️ `uploadArchivo()`/`destroyArchivo()` de Clientes **se quedan en la ficha**, pero con `back()` y no con `redirect()->route('clientes.edit', $cliente)`: el redirect armado a mano pierde el `?volver=` y rompe la vuelta al listado en silencio. Hay un test que lo fija.
- **Al guardar una ficha se vuelve al listado**, no se queda en la ficha. Hasta el 21/9/2026 Clientes/Artículos/Proveedores se quedaban y Users/Roles volvían: ahora los cinco hacen lo mismo.
- ⚠️ `Components/Pagination.vue` usa **`preserveScroll` y NO `preserveState`**: sin el primero cambiar de página tira al tope, y el segundo no compra nada (las props viajan enteras igual) a cambio de dejar `userToDelete`/`roleToDelete` apuntando a filas de la página anterior — hoy el remonte es justamente lo que los limpia. Tampoco lleva `replace`: paginar tiene que dejar entrada en el historial.
- Los tests viven en `tests/Feature/VueltaAlListadoTest.php` y usan **`->from(...)`** para simular de dónde venía el usuario. ⚠️ Un test que le pegue a un `sync()` necesita `Queue::fake()`: si no, el job sale a buscar el ERP de verdad y el test tarda 70 segundos.

### Ordenamiento por columna de los listados
Los 11 listados del panel ordenan haciendo clic en el encabezado. **Solo en desktop**: las `TableCard` de mobile no tienen encabezados y heredan el orden que venga.
- **Backend**: trait [OrdenaListados](app/Http/Controllers/Concerns/OrdenaListados.php), con `orden()` (devuelve el pedido ya validado, para la vista) y `aplicarOrden()`. Cada controller declara su `ordenables()`: **clave = lo que viaja en `?sort=`, valor = la expresión SQL**, así la URL nunca expone un nombre de columna. El valor puede ser una columna, un array (`'nombre' => ['name', 'apellido']`) o una `Closure` para lo que no es columna (subconsulta, `withCount`, `CASE`).
- **Frontend**: componente [ThOrdenable.vue](resources/js/Components/ThOrdenable.vue) (puro: recibe el orden, emite la clave; `campo` en `null` = no ordenable) + composable [useOrdenamiento.ts](resources/js/composables/useOrdenamiento.ts) (toggle + `router.get`). Están separados a propósito: así **Sectores**, que ordena en el cliente, reusa el mismo `<th>` sin arrastrar un `router.get` que ahí no tiene sentido.
- Cuatro reglas que es fácil olvidarse de repetir en la pantalla número siete:
  1. **Whitelist obligatoria.** Sin ella `?sort=password` es una inyección de nombre de columna.
  2. **Una clave desconocida cae en silencio al orden por defecto, no da 422**: los listados se comparten por link y un `?sort=` viejo tiene que seguir abriendo la pantalla. Por eso `sort` se valida como `['nullable','string','max:40']` y **nunca** con `Rule::in()`.
  3. **Desempate final por `id`, en el mismo sentido que la columna elegida.** Sin él la paginación repite o saltea filas cuando hay empates; en sentido contrario, dos filas empatadas se ven en un orden al ordenar A→Z y en el otro al invertir.
  4. **El orden vuelve a la vista ya validado** (prop `orden`), para que la flecha del encabezado no mienta.
- ⚠️ **Trampas concretas**, todas encontradas en el camino:
  - En Artículos/Clientes/Proveedores el `orderBy` vivía dentro del `filtrados()` que comparten con el export. Hay que sacarlo y pasarlo como el callback `$porDefecto`: encadenado primero, el `?sort=` queda de criterio secundario y **no hace nada**. A cambio, el **export hereda el orden de la pantalla**, que es lo correcto ("lo que ves es lo que baja").
  - En los controllers que validan filtros (Observaciones, Bitácora, Bajas) hay que sumar `sort`/`dir` a las reglas o `validate()` los descarta **en silencio**.
  - Las columnas de relación van con **subconsulta en el ORDER BY, nunca con un join**: la query devuelve el modelo entero y un join traería el `id` de la otra tabla pisando el del modelo.
  - Supervisor y gerente en Users necesitan un **self-join aliaseado** (`from('users as supervisores')`): sin el alias, `whereColumn('users.id', 'users.supervisor_id')` compara la tabla consigo misma y devuelve el nombre del propio usuario. Es el bug que no da error.
  - En Ventas, `sub_total` entra en la whitelist **solo con el permiso `ventas.montos`**: dejarla siempre filtraría el dato por ordenamiento (`?sort=sub_total&dir=desc` = la venta más cara arriba). **Lote** y **remito** no son ordenables (el primero se adjunta después del paginado con clave compuesta; el segundo es un entero sin serie con 29% de repetidos).
  - El estado de Observaciones ordena por el **orden del flujo** (`CASE` armado con `array_keys(Observacion::ESTADOS)`), no alfabéticamente.
- **Compras no se toca**: ya ordena en el cliente por diseño (el dataset viaja entero) y su `<th>` denso es propio de esa tabla.

### No Conformidades (NC)

`/no-conformidades`. Incumplimientos confirmados que se investigan, se tratan y se verifican. Dos fuentes, y **cuando se contradicen manda el formulario**:
- **`docs/IT- PARA LA GESTIÓN DE NO CONFORMIDADES EN EL SISTEMA.docx`** — el instructivo operativo. Manda sobre `ARQUITECTURA-SGO.md`, que solo nombraba la tabla.
- **`Formulario_Informe_de_Desvio.xlsx`** — el papel que la gente ya usa. Siete secciones numeradas, en orden fijo. La ficha y el PDF lo replican, y el 24/9/2026 el cliente confirmó cuatro puntos donde el papel le gana al instructivo (ver abajo).

⚠️ **"NC" significa dos cosas distintas en la documentación del proyecto.** Acá es **No Conformidad**. En `Especificacion-Tecnica-SGO-v3.docx` §5.5 y §9.1, "NC" es **Nota de Crédito** del ERP (`nota_credito_erp_id`, *"Genera NC en el ERP con el monto especificado"*). No tienen nada que ver. Un pedido de "incidencia Facturas vs NC por cliente" es lo segundo y sale de `ventas.cod_comprobante`, no de acá.

**Estado de la implementación**: el módulo está completo de punta a punta — alta, aprobación/devolución/rechazo, investigación con las 6M, contención, plan de acción, carga de avance con evidencias, verificación de eficacia, derivación a un desvío nuevo, cierre, reapertura/cancelación de super-admin, el **informe imprimible** con el layout del formulario, el **vínculo con observaciones en las dos direcciones** y los **recordatorios de plazos** (`nc:recordatorios`). Lo único pendiente del módulo es el envío real de mails, que depende de activar Resend en el servidor y no de este código.

**La máquina de estados** (§4.1) vive en `NoConformidad::ESTADOS` y `NoConformidad::TRANSICIONES`, y el controller la hace cumplir con `exigirTransicion()`:

`borrador` → `pendiente_aprobacion` → `abierta` → `plan_accion` → `en_implementacion` → `verificacion_eficacia` → `cerrada`, con dos salidas laterales: **devuelta** (vuelve a `borrador`) y **rechazada** (terminal).

⚠️ **Desde `verificacion_eficacia` solo se cierra.** Un resultado ineficaz **no** reabre la NC — ver más abajo.

- ⚠️ **El `numero` se asigna al APROBAR, no al crear** (§4.4). Es la diferencia de fondo con `Observacion`. Una NC en borrador o rechazada tiene `numero = null`, y eso **no es un dato faltante**: la pantalla dice "Sin número" y explica por qué, en vez de un guion mudo. Por eso la columna es `nullable` pero igual `unique`.
- ⚠️ **"Pendiente de evaluación" no es un estado**: es uno de los resultados posibles de la verificación (§4.7). La NC se queda en `verificacion_eficacia` hasta que pase el tiempo necesario.
- ⚠️ **Una NC rechazada no se borra** (§4.3): queda como antecedente. Hay un test que lo fija.

### ⚠️ Delegación: `nc.gestionar` ya NO es lo único que habilita gestionar

Hasta el 25/9/2026 toda la gestión operativa pasaba por Calidad, porque `nc.gestionar` era la única llave. El cliente lo corrigió ese día: *"Calidad no debería intervenir en la gestión operativa de cada acción (…) **no va a ser responsable en todas las NC**"*. Hay **dos capas de delegación**, y confundirlas es el error fácil:

- **Responsable del caso** (`non_conformities.responsable_id`, nullable). Hace todo lo que hace Calidad sobre ESE caso —investigación, contención, causa raíz, plan, verificación, mover de etapa y **cerrar**— sin tener el permiso global. `NoConformidadPolicy::gestionar()` es `$user->can('nc.gestionar') || $nc->responsable_id === $user->id`. Calidad conserva acceso a todos los casos, que es lo que le permite destrabar uno cuyo responsable se fue de licencia. **Sin responsable, la NC es de Calidad** — es el estado en el que nace. ⚠️ Desde el 28/9/2026 `update()` también delega en `gestionar()`: hasta entonces el responsable llevaba el caso entero pero **no podía corregir la cabecera**, y había que molestar a Calidad por un typo. ⚠️ Ojo igual: `update()` **no tiene pantalla** — no existe un formulario de edición de cabecera, y el `permisos.editar` que viaja a la ficha no lo usa nadie. El cliente confirmó el 29/9/2026 que la ficha alcanza; si algún día hace falta corregir el encuadre, esa pantalla hay que construirla.
- **Responsable de un renglón** (`non_conformity_actions.responsable_id`, `non_conformity_containments.responsable_id`, que **ya existían y eran decorativos**). Gestiona SU acción de principio a fin: avance, evidencias, descripción, fecha y cancelación con justificación. La regla vive en `app/Policies/Concerns/GestionaRenglonesDeNc.php`, compartido por `NonConformityActionPolicy` y `NonConformityContainmentPolicy` (auto-descubiertas) — escrita una sola vez porque es la misma y dos copias se desincronizarían.

Cuatro cosas que no hay que romper:

- ⚠️ **Las rutas por renglón NO van bajo `can:gestionar,noConformidad`.** Ese middleware mira la NC entera y bloquearía al responsable de una acción **antes** de que el controller llegue a chequear la fila. Están fuera del grupo a propósito, y autorizan con `$this->authorize('gestionar', $accion)` — contra el renglón, no contra la NC. Lo mismo vale para `asignarResponsable`, porque el responsable actual puede derivar sin tener `nc.gestionar`.
- ⚠️ **Borrar no es del responsable del renglón**, y por eso hay una habilidad `eliminar` aparte en las dos Policies de renglón. Su salida es **cancelar con justificación**, que deja rastro; borrar lo borra. Hay un test que lo fija.
- ⚠️ **Pasar la posta sin pasar por Calidad**: `asignarResponsable` la tienen `nc.gestionar`, **el responsable actual** y quien aprueba mientras la NC está en `pendiente_aprobacion`. Es un pedido explícito del cliente: sin eso, cada licencia obliga a molestar a Calidad, que es el cuello de botella que este cambio saca.
- ⚠️ **El cierre lo hace el responsable del caso**, no Calidad. Decisión del cliente; Calidad lo ve y puede intervenir, pero no es un paso obligatorio.

**Avisos** (`app/Notifications/NoConformidadNotification.php` y sus cuatro hijas): `NoConformidadAsignadaNotification` al designar el responsable del caso, `AccionAsignadaNotification` al asignar un renglón —**la misma clase para el plan y para la contención**, porque para quien la recibe la pregunta es la misma—, más `AccionVencidaNotification` y `VerificacionPendienteNotification`, que manda `nc:recordatorios`. Molde de `ObservacionNotification` pero **sin el canal `broadcast`**: las NC no tienen toast en vivo y sumar un canal que nadie escucha solo agrega un job por aviso. `viaConnections()` manda `database` a `sync`, así la campana funciona sin worker. ⚠️ **No se avisa a quien hizo la asignación** (`auth()->id()`), y solo **al cambiar** de responsable, no en cada guardado. Todo va en `try/catch` que loguea: la fila ya se guardó y un fallo al notificar no puede devolver un error.

**Vínculo con observaciones** (§5): muchos-a-muchos vía `non_conformity_observation` — está pedido por escrito en `GUIA-FUNCIONAL-SGO.md`: *"vincular una no conformidad a varias observaciones"*. ⚠️ `sync()` **no dispara el evento `updated`**, así que la entrada de bitácora del vínculo se escribe **desde el controller**, no desde el observer. Mismo caso y mismo remedio que `ObservacionController::sincronizarNotificados()`. Se guardan los **números**, no los ids: la bitácora es un registro histórico.

Hasta el 28/9/2026 el pivot existía pero **ninguna pantalla podía escribirlo**: el único camino era el `update()` del controller, que ningún formulario usaba. Ahora tiene sus dos puertas:
- **Desde la observación**: `POST /observaciones/{observacion}/derivar-a-nc` (`crearDesdeObservacion`) crea el desvío en borrador con el encuadre precargado y los vincula. Pide `nc.create` **y** poder gestionar esa observación.
- **Desde el desvío**: `PUT /no-conformidades/{nc}/observaciones` (`vincularObservaciones`), con un buscador (`GET /observaciones/buscar`, `SelectorMultipleAsync`). ⚠️ **Va bajo `gestionar`, no bajo `update`**: `update` es más angosto y dejaría afuera al responsable del caso, que es justamente quien necesita vincular. Hay un test que lo fija.
- **En el alta**: el mismo selector va en `Create.vue` (29/9/2026), así un desvío puede nacer ya vinculado. `store()` las sincroniza desde siempre; lo único que faltaba era el campo en pantalla.

⚠️ **Las tres puertas validan igual.** Hasta el 29/9/2026 `store()` y `update()` leían `observaciones` **crudo** del request —`validarDatos()` no las incluía— y lo mandaban derecho a `sync()`: un id inventado entraba sin pasar por ninguna regla. Esa regla (`array` + `exists:observations,id`) está ahora en `validarDatos()`, por donde pasan los dos, y hay un test que lo fija.

⚠️ **La observación derivada queda en `derivada_nc` y se cierra a mano, por separado** (decisión del cliente del 28/9/2026). No se cierra sola al cerrar el desvío. Ese estado **cuenta como abierto** en `Observacion::ESTADOS_ABIERTOS` —el reclamo no está resuelto, está escalado— y ⚠️ **no hay que confundirlo con `derivada`**, que es la derivación entre sectores y sigue pendiente. Son dos estados con nombres parecidos y por eso la etiqueta del segundo se escribe entera: "Derivada a No Conformidad".

**Bitácora propia e inmutable** (`non_conformity_history`), molde exacto de `observation_history`: §7 exige que "la información histórica no podrá eliminarse ni reemplazarse", y el modelo lo hace cumplir lanzando excepción en `updating`/`deleting`, no solo por convención. El reparto con el observer es el mismo que en Observaciones: **el observer escribe el "De X a Y"** y sella `aprobada_at`/`cerrada_at` en `saving()`; **el controller escribe el porqué** (los motivos de texto libre de una devolución, un rechazo, una cancelación o una reapertura), que es lo único que el observer no puede ver.

⚠️ **CAPA no es una entidad aparte: es el plan de acción.** Las acciones viven en `non_conformity_actions` (tabla hija, N por NC) y `non_conformities.requiere_capa` es la determinación que se toma durante la investigación, no un disparador de otra entidad. `ARQUITECTURA-SGO.md` preveía una tabla `capas` con ciclo de vida propio; el instructivo es posterior y más concreto, así que manda.

⚠️ **Cada acción tenía un `tipo`** (corrección / correctiva / preventiva) y se sacó el 24/9/2026: el formulario no tiene esa columna —su tabla es Acción / Responsable / Plazo— y el cliente confirmó que no hacen la distinción, así que era un campo obligatorio que se completaba al azar. No reponerlo sin volver a preguntar.

⚠️ **La contención (sección 3) es una tabla hija, no tres columnas.** `non_conformity_containments` (fecha, acción, responsable), porque el formulario la dibuja como tabla y a veces se toman varias medidas.

⚠️ **Y se guarda FILA POR FILA, no la lista entera.** Nació como un solo `PUT` que borraba y rehacía todo (el criterio del checklist de clientes). Dejó de servir el 25/9/2026, cuando el responsable de una fila pasó a poder editarla: al mandar el array completo **estaría reescribiendo las filas de los demás**. Hoy son `POST` / `PUT {contencion}` / `DELETE {contencion}`, mismo molde que el plan de acción. Hay un test que fija esa regresión.

⚠️ **La sección 3 es la ÚNICA que se escribe ANTES de la aprobación** (29/9/2026). Hasta entonces compartía la habilitación con la investigación, o sea que recién se podía cargar con la NC ya `abierta` — al revés de cómo pasa en la planta, donde lo primero que se hace al detectar un desvío es contenerlo y el papelerío viene después. Quien aprueba además necesita leer qué se hizo para decidir, y por eso **los botones Aprobar / Devolver / Rechazar aparecen también junto a la sección 3**, con el mismo `permisos.aprobar` que los del encabezado.

- **La llave es `NoConformidadPolicy::cargarContencion()`**, no `gestionar()`: `gestionar() || (estado ∈ {borrador, pendiente_aprobacion} && creado_por === user)`. Sin esa segunda mitad, quien carga el desvío —*cualquier usuario*, §6— no podría escribir la contención que él mismo tomó, porque en borrador no es responsable del caso ni tiene `nc.gestionar`. Son los **dos** estados previos a la aprobación y no solo `borrador`: mientras espera el visto bueno la medida puede cambiar, y una devolución lo manda de vuelta a borrador igual.
- ⚠️ **La ruta `contencion.store` está FUERA del grupo `can:gestionar,noConformidad`**, aunque sea una ruta de NC y no de renglón — mismo motivo que las rutas por renglón y `asignarResponsable`: el middleware mira la NC entera y bloquearía antes de que el controller pueda aplicar la regla fina.
- ⚠️ **La excepción NO vive en `GestionaRenglonesDeNc`**, que es el lugar obvio: ese trait lo comparten la contención y el plan de acción, y meterla ahí le abriría al creador los renglones del plan. Hoy sería inerte —un plan no existe en borrador— pero es una regla más ancha que la pedida, escrita justo donde nadie la va a volver a mirar. Vive en `NonConformityContainmentPolicy`, que la suma a la del trait.
- ⚠️ **El límite tiene test propio**: ya aprobada, el creador sin `nc.gestionar` **no** puede cargar contención. Sin ese test la excepción se ensancha sin que nadie se entere.
- En el front, `seccionesHabilitadas` tiene **`contencion` como flag propio** (viva en todo estado menos `rechazada` y `cancelada`) y `Contencion.vue` recibe `permisos.contencion`, **no** `permisos.gestionar`.

⚠️ **El `motivo` es texto libre**, no una lista. El instructivo lista ocho orígenes posibles (§2) y así estaba; el formulario lo escribe a mano ("Mala implementación de código de barras") y ninguna de las ocho describe un caso concreto. Como consecuencia **entró en `scopeBuscar()`**: el buscador es la única forma de encontrar una NC por su motivo, porque un filtro desplegable ya no es posible.

**Las tres reglas que traban el avance de etapa**, todas validadas en el controller:
- **Investigación → Plan de acción**: `investigacionCompleta()` exige `investigacion` y `causa_raiz`. ⚠️ **Solo esas dos**, porque es lo único que §4.4 pone como condición (*"mientras la investigación y el análisis de causa se encuentren incompletos"*). La etapa pide bastante más (contención, alcance, afectados, riesgo), pero convertir una recomendación en un bloqueo frenaría a alguien por un campo que su caso no necesita — "productos y lotes afectados" no aplica a una NC de proceso. Hay un test que lo fija.
- **Plan de acción → En implementación**: `tienePlanDeAccion()` exige al menos una acción (§4.5). Un plan vacío no es un plan.
- **En implementación → Verificación de eficacia**: `accionesResueltas()` exige que no quede ninguna acción en `pendiente`, `en_curso` ni `vencida` (§4.6). ⚠️ Una **cancelada no cuenta como pendiente**, pero cancelar exige motivo: es la salida para la acción que dejó de tener sentido, y el motivo es lo que la distingue de abandonarla.

**Avance de una acción** (§4.6, `actualizarAvance()`): estado, qué se hizo y evidencias, que van a `subcarpeta: 'acciones'` y quedan atadas a la entrada de bitácora del avance.
- ⚠️ **`vencida` no se puede elegir a mano**, ni en la pantalla ni en el backend: es derivado de que pase la fecha prevista, y ofrecerlo lo convertiría en "atrasada pero la sigo", que es justo lo que el estado tiene que delatar solo. Hay un test que lo fija. Quien lo escribe es `nc:recordatorios` (ver más abajo).
- **Completar sin cargar fecha real sella hoy**: es el dato del que sale el cumplimiento en fecha, y dejarlo en `null` lo rompería.
- **Quitar una acción se ofrece solo mientras la NC está en `plan_accion`.** Después, alguien ya se comprometió con ella: la salida es cancelarla con justificación, que deja rastro. El backend igual permite el borrado (es la misma habilidad `gestionar`); la que no lo ofrece es la pantalla.

### Recordatorios de plazos (`nc:recordatorios`)

Tarea diaria (07:00) con dos trabajos, y es **quien por fin escribe el estado `vencida`** de una acción.

- **Acciones vencidas**: las que pasaron su `fecha_prevista` y siguen en `pendiente` o `en_curso` pasan a `vencida`, y se avisa **al responsable de la acción y al del caso** — son dos personas distintas desde la delegación del 25/9/2026 y las dos necesitan saberlo. Quedan afuera las de una NC que ya no está en `ESTADOS_ABIERTOS`: sin ese filtro seguirían venciendo para siempre.
- **Verificación de eficacia**: avisa cuando llegó `fecha_verificacion_prevista` y todavía no hay `resultado_eficacia`. Se mira desde `en_implementacion` y no solo desde `verificacion_eficacia`, porque la gracia es enterarse de que llegó el momento.

⚠️ **La idempotencia son DOS mecanismos distintos, y confundirlos rompe uno de los dos:**
- En las acciones alcanza el propio cambio a `vencida`, que las saca del filtro (mismo truco que `alerta_nivel` en observaciones).
- En la verificación **no cambia ningún estado** —la NC sigue donde estaba— así que necesita una marca propia: `non_conformities.verificacion_avisada_at`. Sin ella, la tarea avisaría de lo mismo todos los días.

⚠️ **`fecha_verificacion_prevista` NO es `fecha_seguimiento`.** La primera mira al futuro (cuándo se va a verificar) y **se carga al armar el plan de acción**, sección 5; la segunda es registro (cuándo se verificó), sección 6. Cargarla en la sección 6 sería inútil: esa sección recién se habilita al llegar a la etapa de verificación, y para entonces ya es tarde para avisar. Es un pedido explícito del cliente del 28/9/2026 —*"el usuario tiene que cargar la fecha de verificación de eficacia"*— para poder ajustarla según el tipo de desvío en vez de tener un plazo fijo para todos. **Cambiar la fecha limpia `verificacion_avisada_at`**, así el aviso vuelve a salir en la fecha nueva.

⚠️ **Una NC sin responsable cae en Gestión de Calidad** para el aviso de verificación — es el estado en el que nace, y sin ese fallback el recordatorio se perdería justo en los casos sin dueño. Se filtra con `whereHas`, **nunca** con el scope `permission()` de Spatie, que tira excepción si el permiso no está creado: una tarea agendada no puede caerse por eso. Misma trampa que `User::role()` en el alta del portal.

**Cierre** (§4.8): `condicionesDeCierre()` devuelve las **cinco** condiciones que traban, como `{clave => bool}`, y `puedeCerrarse()` las exige todas. Viajan a la ficha en la prop `condicionesCierre` y se dibujan como checklist desde que la NC entró al circuito — sirve de hoja de ruta, no solo de traba al final. Si alguien intenta cerrar igual, el controller responde **cuál falta** (`condicionesPendientes()`), no un botón mudo. ⚠️ Las etiquetas del front están en `condicionesCierreLabels` (`lib/nc.ts`) y **el orden de la checklist es el de ese objeto**, no el del array PHP: una condición nueva en el backend que no esté ahí no se muestra, y la persona no entiende por qué no puede cerrar.

⚠️ **§4.8 enumera SIETE condiciones; dos dejaron de trabar el 28/9/2026** y pasaron a `advertenciasDeCierre()`, que la ficha muestra en el modal de cierre sin bloquear (prop `advertenciasCierre`):
- **Las evidencias adjuntas.** El cliente lo confirmó por escrito ("NO, no es obligatorio"): hay desvíos que se resuelven sin nada que adjuntar, y exigirlo obligaba a subir un archivo de relleno.
- **Las observaciones vinculadas cerradas.** Desde que una observación derivada **se cierra a mano y por separado**, esta condición producía un **bloqueo mutuo**: el desvío esperaba a la observación y la observación esperaba el resultado del desvío, y ninguno de los dos cerraba nunca. Hay dos tests que fijan las dos mitades.

⚠️ **Un resultado ineficaz abre un desvío NUEVO; no reabre éste.** §4.7 del instructivo dice que la NC "deberá regresar" a investigación y así estaba implementado hasta el 24/9/2026. El formulario tiene una celda **"Nuevo desvío N°"** al lado del resultado, y el cliente confirmó ésa. Cuatro consecuencias:
- `non_conformities.reemplaza_a_id` es una FK a sí misma que vive en la NC **nueva** y apunta hacia atrás. Con una sola columna se leen las dos direcciones (`reemplazaA` es el `belongsTo`, `reemplazadaPor` el `hasOne`) y no hay un par de claves circulares que se desincronicen cuando una escritura falla a mitad de camino.
- Guardar "ineficaz" **no mueve el estado ni crea nada**. Abrir el desvío es un paso aparte (`derivar()`), porque crea un caso nuevo y eso no puede pasar de callado al guardar un formulario.
- La NC derivada **nace en borrador y pasa por aprobación como cualquier otra**: no hereda la aprobación de la anterior. Se le precarga el encuadre (tipo, sector, cliente/proveedor) pero **nunca la investigación ni el plan** — si esas acciones hubieran servido, no estaríamos abriendo un desvío nuevo.
- La condición de cierre `eficaz` **no es** "el resultado dio eficaz" a secas: es "eficaz, **o** ineficaz con el desvío nuevo ya abierto". Sin esa segunda mitad una NC ineficaz no podría cerrarse nunca, y el formulario tiene fecha y responsable de cierre para los dos casos.

⚠️ **"Cerrada queda bloqueada para edición" no aplica al super-admin.** La Policy devuelve `false` en `update` y `gestionar` cuando la NC está finalizada, pero `Gate::before` saltea las dos — igual que en todo el resto de la app. Verificado en el vhost: un super-admin puede registrar un avance sobre una NC cerrada y queda en la bitácora. Es coherente con que la reapertura y la cancelación sean suyas, pero conviene saberlo antes de leer §4.8 como una garantía dura.

⚠️ **Reabrir borra `cerrada_at`/`cerrada_por` pero conserva el número y la aprobación original.** Lo primero lo hace `NoConformidadObserver::marcarCierre()` al salir del estado final; sin eso, un segundo cierre mostraría la fecha del primero. Lo segundo es a propósito: la NC es la misma, no una nueva. Hay un test que fija las dos mitades.

**Análisis de causa raíz por las 6M** (§4.4, pedido también en `GUIA-FUNCIONAL-SGO.md`): `causa_raiz_factores` es un JSON `{factor: texto}` con **solo los factores que aportaron algo**, no una lista de tildes — de un Ishikawa lo que sirve es *qué* aportó cada factor. El catálogo es `NoConformidad::FACTORES_CAUSA` y el controller descarta lo que no esté en él. ⚠️ **El orden de esa constante es el del formulario en papel** (Hombre, Máquina, **Entorno**, Material, Método, Medida) y es el que dibuja la pantalla y el PDF: el front itera el objeto tal cual viene. ⚠️ Sin ningún factor cargado queda en `null` y no en `[]`: "no se analizó por factores" y "se analizó y ninguno aplicó" se leen distinto.

⚠️ **Las rutas de acciones NO usan `scopeBindings()`.** Laravel resuelve el hijo buscando la relación por el **plural inglés** del parámetro de ruta: `{accion}` → `accions()`, y la relación se llama `acciones()`. Renombrar una de las dos para que el pluralizador acierte una palabra en español es peor que verificar la pertenencia a mano, así que lo hace `exigirQueSeaDeLaNc()` con un `abort_unless`. Es la misma trampa que el `{attachment}` de los adjuntos de cliente, resuelta al revés — y hay un test que la cubre.

**La ficha replica el formulario en papel.** `Show.vue` dibuja las **siete secciones numeradas, siempre presentes y en orden**; las que la etapa todavía no habilitó se ven en gris con el motivo al lado. ⚠️ **No se esconden a propósito**: quien abre una NC recién aprobada no tendría forma de saber que después viene un plan de acción y una verificación. El papel muestra el recorrido entero desde el minuto cero, y esa es la ventaja que se está copiando. El wrapper es `Components/NoConformidad/SeccionNc.vue`; cada sección es un componente propio (`Investigacion`, `Contencion`, `CausaRaiz`, `PlanDeAccion`, `Verificacion`), y las secciones 6 y 7 van juntas porque se completan en el mismo momento.

⚠️ **`Investigacion.vue` (sección 2) y `CausaRaiz.vue` (sección 4) guardan contra el MISMO endpoint.** Por eso `guardarInvestigacion()` solo normaliza `causa_raiz_factores` **cuando vino en el request**: si lo hiciera siempre, guardar la investigación borraría las 6M que cargó el otro bloque, en silencio.

**El informe imprimible** (`resources/views/pdf/no-conformidad.blade.php`, ruta `no-conformidades.pdf`, gateado con `nc.view`) replica el layout del Excel: cabecera en grilla y las siete secciones con los mismos títulos, más tres anexos que el papel no puede dar (observaciones vinculadas, imágenes y la bitácora que exige §7). ### "Bitácora" son dos cosas — no confundirlas
- **La bitácora de un caso**: el historial de UNA observación (`ObservationHistory` / tabla `observation_history`, `Components/BitacoraObservacion.vue`, embebido en `Show.vue` y en el modal de `Index.vue`). Inmutable: el modelo bloquea `updating`/`deleting`, y no hay ruta de edición ni de borrado.
- **La sección Bitácora** (`/bitacora`, `bitacora.index`, permiso `bitacora.view`, `Admin\BitacoraController` + `Pages/Admin/Bitacora/Index.vue`): la vista **transversal** de `observation_history` completa, filtrable por usuario, sector, acción y fechas.

Los helpers para interpretar el JSON `cambios` (que cambia de forma según `accion`) están en `resources/js/lib/bitacora.ts`, **compartidos por las dos vistas** — duplicarlos garantizaba que se desincronizaran.

⚠️ Esta sección se llamaba **"Auditoría"** hasta el 30/7/2026. Se renombró por completo (URL, ruta, permiso, controller, carpeta, test) porque **"Auditoría" va a ser otra sección con otra funcionalidad**, y hacía falta liberarle el nombre. Una migración renombra la fila `auditoria.view` → `bitacora.view` en `permissions` para no dejar el nombre viejo ocupado ni que los roles pierdan el acceso. **No reusar `auditoria.*` para nada que no sea esa sección futura.** La subcarpeta de disco `observaciones/{numero}/bitacora/` (adjuntos de comentarios) es de la bitácora por-caso y no se tocó — son paths de archivos ya subidos.

### Carga manual de observaciones (panel)
- El botón "+ Nueva" del Dashboard lleva a `Admin/Observaciones/Nuevo.vue` (`observaciones.nuevo`), un selector de 3 tarjetas: **externa**, **interna** y **No Conformidad** (esta última lleva a `/no-conformidades/crear`, que es otro módulo — ver arriba). Los dos formularios de observación están gateados por el permiso `observaciones.edit` (`create`/`store` en `Admin\ObservacionController`, rutas `observaciones.create`/`observaciones.store`).
- **Externa** (`Create.vue`): réplica del formulario del portal público (mismos campos + productos repetibles para `falla_producto`) más **Sector responsable** y **Responsable**. Estado inicial `pendiente_clasificacion`.
- **Interna** (`CrearInterna.vue`): formulario **dirigido por taxonomía**. El **Sector** elegido filtra el **Tipo de incidencia**, y cada tipo define su bloque variable **"Datos específicos"** (guardado en la columna JSON `observations.datos_especificos`). La taxonomía completa vive en **`config/incidencias.php`** (clave = slug del sector) — agregar un tipo nuevo es solo config, sin tocar código. `app/Support/TaxonomiaIncidencias.php` la lee y genera las **reglas de validación dinámicas** (`datos_especificos.<campo>`). Incluye clasificación en el alta (Prioridad, Tipo de caso; la Prioridad se sugiere según el Tipo de caso); estado inicial `clasificada`. La columna `tecnovigilancia` existe (la usa el Dashboard) pero **no** se carga desde este formulario. El componente `Components/CampoDinamico.vue` renderiza cada campo (text/textarea/number/date/select/radio) desde su def.
- **Producción es un solo sector con dos líneas adentro.** Tubos y Apósitos **no** son sectores separados: son subgrupos de tipos, vía la clave opcional `grupo` de cada tipo en `config/incidencias.php`, que `CrearInterna.vue` renderiza como `<optgroup>` del select de Tipo de incidencia. Un solo equipo, un solo plazo, una sola bandeja de derivación. Los sectores que no declaran `grupo` (todos los demás) caen juntos en "Incidencias del sector" y no cambian en nada.
- El tipo de campo `time` (`<input type="time">`, validado con `date_format:H:i`) **sí usa el widget nativo**, a diferencia de las fechas, que van con el texto enmascarado de `InputFecha`: no hay un equivalente propio para horas. "Fecha y hora" se parte en dos campos (uno `date` y uno `time`) en vez de un `datetime`, para no meter el único date picker nativo del panel.
- ⚠️ **`deploy.sh` también reseedea `SectorSeeder`**, por el mismo motivo que los permisos: un sector nuevo en el código queda invisible en producción hasta que alguien lo corra a mano. Es idempotente (`firstOrCreate`), así que no pisa el `dias_gestion` que se haya editado desde el ABM.
- `store()` en `Admin\ObservacionController` **bifurca por `origen`**: `interna` → `storeInterna()` (validación dinámica vía el helper); el resto → flujo externa. `create()` bifurca igual para devolver `Create` o `CrearInterna`.

## Entorno

- **DB**: el `.env` de este entorno de desarrollo apunta a **MySQL** (`DB_CONNECTION=mysql`, DB `sgo-tublood`), no a SQLite pese a lo que sugeriría un setup default de Laravel — verificar `.env` antes de asumir. Los **tests** son la excepción: `phpunit.xml` fuerza `DB_CONNECTION=sqlite` / `DB_DATABASE=:memory:` sin importar el `.env`.
- **Prod**: droplet propio en DigitalOcean (Ubuntu 24.04, nginx + PHP 8.3-FPM + MySQL en la misma máquina). Deploy con `./deploy.sh` corrido a mano por SSH — no hay CI/CD. Hace `git pull --ff-only` de la rama actual (hoy se despliega directo desde `feature/codigo-producto-y-espanol`, **no** desde `main`, que quedó desactualizada), reinstala dependencias y **compila los assets** si cambiaron, migra, reseedea `RolesAndPermissionsSeeder` y `SectorSeeder` (agregar un permiso o un sector en el código no alcanza: sin este paso quedan invisibles en producción hasta que alguien lo corra a mano), regenera cachés y hace `queue:restart` — sin eso el worker sigue con el código viejo en memoria. El armado inicial del servidor está en **[deploy/README.md](deploy/README.md)** con sus scripts (`deploy/provision.sh`, el service de systemd y el server block de nginx).
- ⚠️ Hasta el 19/8/2026 la app vivía en **hosting compartido (Hostinger)**, y de ahí venían tres limitaciones que ya no aplican: no corría el scheduler, no corría ningún queue worker (los jobs se acumulaban sin procesar), y no se podía instalar `pdo_sqlsrv`, así que **proveedores y ventas nunca se sincronizaban**. Por eso esas dos tareas se auto-apagan con `->when($erpConfigurado)` en `routes/console.php` — el guard sigue teniendo sentido para cualquier entorno sin la extensión, pero en el droplet están encendidas.
- ⚠️ **`public/build/` ya no se versiona.** Se versionaba solo porque el hosting compartido no tenía Node; el droplet sí, y `deploy.sh` corre `npm run build`. Si tocás el frontend, ya no hace falta commitear los assets.
- **Queue**: driver database (sin Redis en dev)
- **Mail**: **Resend** (`resend/resend-php`; el mailer y `services.resend.key` ya venían en el scaffold de Laravel). En **dev queda en `MAIL_MAILER=log`** a propósito — los mails se leen en `storage/logs/laravel.log` y no hay riesgo de mandarle una prueba a un cliente real. Para activarlo: `MAIL_MAILER=resend` + `RESEND_API_KEY`, y `MAIL_FROM_ADDRESS` **tiene que ser de un dominio verificado en Resend** o rechaza el envío. Los tests nunca mandan nada: `phpunit.xml` fuerza `MAIL_MAILER=array`.
- **Alias Vite**: `@/` → `resources/js/`
- **Laravel Boost**: `laravel/boost` está instalado y expone un servidor MCP (`.mcp.json` → `php artisan boost:mcp`) con acceso a schema de DB, logs de error, `last-error` y búsqueda semántica de docs de Laravel. Útil para inspeccionar el estado real de la app sin escribir scripts de tinker.

## Testing

PHPUnit corre contra SQLite `:memory:` (forzado por `phpunit.xml`, independiente del `DB_CONNECTION` real del `.env`). Suites en `tests/Feature/`: `ClienteControllerTest`, `ClienteSyncTest`, `ObservacionPublicaTest`, `ObservacionAdminTest`, `ObservacionNotificadosTest`, `CampanaPorRolTest`, `BitacoraObservacionTest`, `BitacoraTest`, `DashboardTest`, `UserControllerTest`, `UserImportTest`, `AlertasObservacionTest`, `NotificacionesVencimientoTest`, `NoConformidadTest`, `RecordatoriosNoConformidadTest`, más `tests/Unit/`. `UserImportTest` arma un `.xlsx` real con PhpSpreadsheet (un `UploadedFile::fake()` genérico no se puede leer); `AlertasObservacionTest` usa `travelTo()` con fechas fijas y `Notification::fake()`. ⚠️ **Fijar la fecha ahí no es cosmético**: los tests que combinan el plazo en días hábiles (`addWeekdays()`) con `travel()` en días corridos fallan según el día de la semana en que se corran — corriendo un jueves, 2 días hábiles caen el lunes y avanzar 3 días corridos llega al domingo. Cualquier test nuevo de alertas tiene que pinchar la fecha en un lunes; `RecordatoriosNoConformidadTest` lo hace por el mismo motivo. Patrón habitual en tests de permisos: helper privado `userWith(...$permissions)` que crea el/los `Permission` con `firstOrCreate` y se los asigna a un usuario de prueba (ver cualquier test de `Admin/*`). Para tests de autorización por objeto (ver `ObservacionAdminTest`), en vez de/además de `userWith(...)` hay que setear `responsable_id` al crear la `Observacion` (o asignar el rol `super-admin`) para que el usuario de prueba pase la Policy. Para correr un solo archivo: `php artisan test tests/Feature/MiTest.php`.

**Nota**: `tests/Feature/ExampleTest.php` (boilerplate de Laravel) falla porque `/` redirige a `/login` (302, no 200) — es preexistente y no relacionado con ningún feature; no darlo por señal de regresión real.
